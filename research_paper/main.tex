\begin{abstract}
Multi-tenant Software-as-a-Service (SaaS) applications often use shared-schema databases to reduce infrastructure and hosting costs. Although this approach makes efficient use of database resources, it also creates challenges in keeping customer data separate. Since multiple organizations store their records in the same tables, tenant isolation depends partly on how application queries are implemented. A missing tenant condition in even one query can allow users to access information belonging to another organization.

This paper presents an evaluation of NexusOps, an operations platform developed using Spring Boot and PostgreSQL. The platform uses two layers of tenant protection: filtering at the Object-Relational Mapping (ORM) level and Row-Level Security (RLS) at the database level. Both mechanisms work together to restrict access to tenant-specific records, rather than relying entirely on application-level checks.

The study examines the system architecture, connection lifecycle management, security properties, and runtime performance. It also introduces a transaction-scoped connection protocol to prevent tenant context from carrying over when pooled database connections are reused. The proposed approach is evaluated through automated security tests, a 16-mutant fault-injection matrix, and performance benchmarks involving 1,000,000 database tuples on PostgreSQL 17. During a concurrency test involving 1,000,000 requests, 100 workers, 32 pooled connections, and 940,000 tenant context transitions, no cross-tenant data leakage was observed. The database-level RLS overhead ranged from 2.3\% to 8.8\% compared with sanitized baselines. Overall, the results indicate that combining ORM-level filtering with database-enforced security can provide an additional layer of tenant protection while keeping the measured performance overhead within the evaluated limits.
\end{abstract}

\section{Introduction}
\IEEEPARstart{M}{any} businesses still rely on spreadsheets, paper records, and messaging platforms to manage their daily operations. Tasks such as tracking sales leads, maintaining inventory, and preparing invoices are often handled through these tools. Although they are easy to adopt, managing business information in this way can lead to errors, inconsistencies, and difficulties in maintaining accurate records. Previous studies by Panko \cite{panko1998} and Powell et al. \cite{powell2009} have also highlighted the frequency of errors in operational spreadsheets, showing how unreliable manual record-keeping can affect business activities.

Cloud-based Software-as-a-Service (SaaS) applications provide an alternative by bringing business operations and data management into a centralized platform. However, operating such platforms also involves financial considerations. Smaller businesses generally have limited budgets for software subscriptions, which makes it difficult for SaaS providers to maintain a separate database or virtual machine for every customer. To address this limitation, many providers use a shared-schema architecture in which multiple organizations store their records within the same database tables \cite{chong2006, aulbach2008, armbrust2010}. This approach improves resource utilization and can significantly reduce hosting costs compared with maintaining separate database environments for each tenant \cite{kabbedijk2015}.

\subsection{Security Challenges in Shared-Schema Databases}
Although shared-schema databases offer practical advantages, they require careful handling of tenant data. Records belonging to different organizations are stored within the same tables and are usually distinguished by a column such as \texttt{tenant\_id}. As a result, database queries must include the appropriate tenant condition to ensure that each organization can access only its own records.

For example, a query retrieving customer information should include a condition such as \texttt{WHERE tenant\_id = :current\_tenant}. If a developer forgets to include this condition while creating a new REST endpoint, reporting query, batch operation, or native SQL statement, the database may execute the query without restricting it to the intended tenant. Depending on the operation, this can expose, modify, or delete records belonging to another organization.

This issue is closely related to Broken Access Control and Broken Object Level Authorization (BOLA), both of which are recognized security concerns in modern application development \cite{owasp2021, owaspapi2023}. The Verizon Data Breach Investigations Report also identifies human-related factors, including configuration mistakes, missing security checks, and credential misuse, as significant contributors to security incidents \cite{verizon2023}. IBM has further reported substantial financial consequences associated with enterprise data breaches \cite{ibm2023}. For SaaS providers, cross-tenant data exposure can directly impair customer confidence, business continuity, and regulatory compliance.

\subsection{The Need for Defense-in-Depth}
The principle of defense-in-depth, discussed by Saltzer and Schroeder \cite{saltzer1975}, emphasizes that critical security mechanisms should not depend on a single protective measure. Applying this principle to multi-tenant databases means enforcing tenant restrictions at more than one level.

At the application level, Object-Relational Mapping (ORM) frameworks such as Hibernate can automatically apply tenant conditions when generating database queries. This reduces the need for developers to manually include tenant filters in every operation. However, ORM-based filtering does not cover every possible database interaction. Native SQL and direct JDBC operations may bypass the ORM layer.

PostgreSQL Row-Level Security (RLS) provides an additional mechanism for controlling which rows can be accessed or modified. With an appropriate policy in place, PostgreSQL evaluates the tenant condition at the database level, providing protection even when an application query does not contain an explicit tenant filter \cite{aws2020, postgresql17docs, postgresql17notes}.

Despite these advantages, adopting database-level RLS introduces practical considerations. One concern is its effect on query execution and overall application performance. Developers may be concerned about additional policy evaluation and its impact on query planning, indexing, and response times. Another concern involves connection pooling. Frameworks such as HikariCP reuse physical database connections across multiple requests, so tenant-specific session information must be managed carefully to prevent one request from affecting another. Database migrations also require attention because newly created tables may be left without the necessary security policies.

These concerns make it important to evaluate not only the security benefits of combining ORM filtering and RLS, but also the way both mechanisms behave during normal application execution.

\subsection{Contributions of This Work}
This paper presents the design and evaluation of NexusOps, an operations management platform developed using Spring Boot and PostgreSQL. The platform combines application-level tenant filtering with database-enforced Row-Level Security to provide two layers of protection for tenant-owned data.

The main contributions of this work are as follows:
\begin{enumerate}
\item \textbf{Transaction-Scoped Connection Protocol:} We describe a connection lifecycle mechanism that binds tenant information to the active database transaction and manages its cleanup when pooled connections are reused.
\item \textbf{Formal Semantics and Security Proof:} We define the operational behavior of tenant-aware query execution and provide an inductive proof to examine non-interference between tenant contexts during connection reuse.
\item \textbf{Automated Schema Verification:} We introduce verification mechanisms that inspect database policies and their expressions, helping identify missing or incorrectly configured RLS policies during schema changes and application startup.
\item \textbf{Security Evaluation:} We evaluate the isolation mechanisms using canary tokens, positive controls, and a 16-mutant fault-injection matrix to examine whether different implementation faults can result in cross-tenant data exposure.
\item \textbf{Engineering and Maintainability Evaluation:} We examine practical aspects of the implementation, including developer experience, zero-downtime schema migrations, and support workflows for tenant diagnostics.
\item \textbf{Performance Evaluation:} We measure the runtime overhead of database-level RLS across different workloads on PostgreSQL 17, using paired benchmark runs and equivalence testing to assess its practical impact.
\end{enumerate}

\section{Background and Related Work}
\label{sec:background}

Multi-tenancy has been explored extensively in database research and enterprise software engineering. As cloud computing became widely adopted, researchers and practitioners investigated various techniques for sharing computing and database resources among multiple organizations \cite{armbrust2010, bezemer2010}.

\subsection{Architectural Strategies for Multi-Tenancy}
Early work on multi-tenant systems classified database architectures into three primary models: database-per-tenant, schema-per-tenant, and shared-schema approaches \cite{chong2006, kabbedijk2015}.

The database-per-tenant model assigns a separate physical or logical database to each customer. This approach provides strong isolation between tenants and simplifies per-customer backup, migration, and resource accounting. However, it requires maintaining numerous database instances or files, which increases infrastructure costs and administrative effort as the number of organizations grows \cite{jacobs2007}.

The schema-per-tenant model groups multiple customers within a single database instance while assigning each organization its own namespace or schema. This reduces instance-level overhead compared with the database-per-tenant approach. Nevertheless, maintaining hundreds or thousands of schemas can strain database management systems during schema migrations, catalog lookups, and metadata operations \cite{weissman2009}.

The shared-schema model places records from all organizations into a single set of tables, using a discriminator column such as \texttt{tenant\_id} to associate each row with its owning tenant \cite{aulbach2008, guo2007}. This model offers high resource density and lowers hosting costs, making it a common choice for enterprise SaaS applications \cite{krebs2012, schiller2011}. However, because tenant records reside alongside one another, preventing unauthorized access across tenant boundaries becomes the primary responsibility of application code and database queries \cite{narasayya2022}.

\subsection{Database-Enforced Row Filtering Mechanics}
PostgreSQL introduced declarative Row-Level Security (RLS) in version 9.5. Its integration with the query planner was further refined in PostgreSQL 17 \cite{postgresql17docs, postgresql17notes}. When RLS is enabled on a table, the database rewrites incoming queries to include the conditions specified by the applicable security policy. This ensures that the policy condition is evaluated as part of the query execution plan, regardless of whether the original query included an explicit tenant filter.

The query-modification approach used by RLS builds on concepts established by Stonebraker and Wong in early relational systems, where access permissions were enforced by rewriting queries prior to execution \cite{stonebraker1974}. Modern database systems implement similar capabilities, including Oracle Virtual Private Database (VPD), Microsoft SQL Server Row-Level Security, and MySQL view-based filtering. These mechanisms allow security rules to be enforced within the database engine rather than relying entirely on application software.

In application development, multi-tenant filtering is often handled at the Object-Relational Mapping (ORM) layer. Frameworks such as Hibernate provide features that automatically append tenant conditions to generated SQL statements \cite{hibernate2025}. While this approach simplifies application code, it does not apply to queries that bypass the ORM layer, such as native SQL statements, reporting queries, or direct database connections.

\subsection{Separating Multi-Tenancy from Role-Based Permissions}
Multi-tenant architectures generally distinguish between two aspects of access control: tenant isolation and user authorization \cite{sandhu1996, ferraiolo2001}.

Tenant isolation determines which organization's data an operation is permitted to access. It establishes a boundary between customers and is typically evaluated before individual user permissions are considered. In NexusOps, tenant identity is represented by an immutable identifier, \texttt{tenant\_id}, which remains associated with the request throughout its execution.

User authorization, by contrast, determines what actions an authenticated user is permitted to perform within their organization. NexusOps manages user permissions through Role-Based Access Control (RBAC), using roles such as \texttt{OWNER}, \texttt{ADMIN}, \texttt{MEMBER}, and \texttt{VIEWER}. These roles govern application-level features, such as creating invoices or viewing reports, but they do not alter the tenant boundary itself.

\subsection{Research Challenges Addressed}
Prior research has addressed shared-schema mapping \cite{aulbach2008}, automated query transformations \cite{stonebraker1974}, and administrative overhead in multi-tenant environments \cite{bezemer2010, kabbedijk2015}. However, relatively few studies have examined the operational interaction between application-tier ORM filtering and database-level Row-Level Security under high-concurrency conditions.

In particular, the behavior of connection pools during repeated tenant context transitions requires careful attention. When physical database connections are reused across different requests, session state must be cleared reliably to prevent tenant information from carrying over. In addition, the performance overhead of evaluating database security policies on modern relational engines warrants empirical evaluation. This paper addresses these questions through an evaluation of NexusOps on PostgreSQL 17.

\section{Threat Model, Formal Semantics and Security Invariants}
\label{sec:threat_model}

To evaluate the security of the dual-layer architecture, we define the threat model, the operational semantics governing query execution, and the formal properties expected of the system.

\subsection{Attacker Capabilities and Trusted Computing Base}
We consider an adversary $\mathcal{A}$ whose objective is to observe, modify, or delete data belonging to a tenant other than their own. The adversary is assumed to have legitimate access to the platform as a registered user of tenant $T_A$ and may attempt to access records belonging to tenant $T_B$, where $T_A \neq T_B$.

The adversary may interact with the system through several vectors:
\begin{enumerate}
\item \textbf{API-Level Manipulation:} The adversary may send manipulated HTTP requests, including altered URL paths, sequential identifier guessing (Insecure Direct Object Reference or IDOR), and forged HTTP headers such as \texttt{X-Tenant-ID} or \texttt{X-Tenant-Slug}.
\item \textbf{Application Implementation Faults:} The adversary may exploit application-level mistakes, such as missing ORM tenant annotations, unparameterized native SQL queries, or repository methods that omit tenant filters.
\item \textbf{Connection-State Bleeding:} The adversary may attempt to benefit from state retention in pooled database connections, where a connection previously used by tenant $T_B$ is reused for a request from tenant $T_A$ without being properly sanitized.
\end{enumerate}

The Trusted Computing Base (TCB) consists of the PostgreSQL database engine, the host operating system kernel, the perimeter query-compilation layer, and the asymmetric JWT signing key used for RS256 authentication.

The dual-layer isolation mechanism is designed to protect against tenant-identification errors and missing access conditions in application code. However, both enforcement layers depend on a shared source of tenant context: the active database session setting, \texttt{app.tenant\_id}.

This dependency is important. If an attacker successfully exploits stacked SQL injection, they may attempt to execute \texttt{set\_config('app.tenant\_id', ...)} directly. Therefore, enabling RLS does not remove the need for secure input handling and query construction. NexusOps uses parameterized query compilation and extended query mode to reduce this risk.

\subsection{Small-Step Operational Semantics}
To describe how queries behave under the proposed dual-layer isolation model, we define a small-step operational semantics.

Let $\mathcal{T} = \{t_1, t_2, \dots, t_n\}$ represent the set of registered tenant identifiers. The empty value, $\emptyset$, represents a missing or unauthenticated tenant context.

The database state, denoted by $\sigma$, maps each relation $T$ to its stored collection of rows, written as $\sigma(T)$. Every row $r$ contains an immutable tenant identifier:
\begin{equation}
r.\texttt{tenant\_id} \in \mathcal{T}
\end{equation}

The state of a physical database connection is represented as $C = (\mathit{id}, \tau, m)$, where $\mathit{id}$ identifies the physical connection, $\tau \in \mathcal{T} \cup \{\emptyset\}$ represents the tenant context currently associated with it, and $m \in \{\mathit{auto}, \mathit{tx}\}$ indicates whether the connection is operating in automatic-commit or transaction mode.

Executing a query $\mathcal{Q}$ produces a result set $\mathcal{R}$ and may update the database state. This transition is expressed as:
\begin{equation}
\langle \mathcal{Q}, \sigma, \tau \rangle \to \langle \mathcal{R}, \sigma' \rangle \label{eq:exec}
\end{equation}

Under dual-layer enforcement, the database applies a tenant-visibility operator $\Pi_\tau$ to the stored relation. This operator retains only those rows whose tenant identifier matches the active context:
\begin{equation}
\Pi_{\tau}(\sigma(T)) = \{ r \in \sigma(T) \mid r.\texttt{tenant\_id} = \tau \land \tau \neq \emptyset \} \label{eq:filter}
\end{equation}

For an authenticated read query $\mathcal{Q}_{\mathit{read}}(T, \phi)$, where $\phi$ represents the application's query condition, the visible result set is:
\begin{equation}
\mathcal{R} = \{ r \in \Pi_{\tau}(\sigma(T)) \mid \phi(r) \}
\end{equation}
The corresponding execution rule is:
\begin{equation}
\frac{\tau \in \mathcal{T} \quad \mathcal{R} = \{ r \in \Pi_{\tau}(\sigma(T)) \mid \phi(r) \}}{\langle \mathcal{Q}_{\mathit{read}}(T, \phi), \sigma, \tau \rangle \to \langle \mathcal{R}, \sigma \rangle}
\end{equation}

If a read query is executed without a valid tenant context, the system returns an empty result set:
\begin{equation}
\frac{\tau = \emptyset}{\langle \mathcal{Q}_{\mathit{read}}(T, \phi), \sigma, \emptyset \rangle \to \langle \emptyset, \sigma \rangle}
\end{equation}

Write operations follow a similar rule. For an operation $\mathcal{Q}_{\mathit{write}}(T, r)$, a record can be inserted only when its tenant identifier matches the active tenant context: $r.\texttt{tenant\_id} = \tau$. In that case, the database state is updated as $\sigma' = \sigma[T \mapsto \sigma(T) \cup \{r\}]$:
\begin{equation}
\frac{\tau \in \mathcal{T} \quad r.\texttt{tenant\_id} = \tau \quad \sigma' = \sigma[T \mapsto \sigma(T) \cup \{r\}]}{\langle \mathcal{Q}_{\mathit{write}}(T, r), \sigma, \tau \rangle \to \langle \{r\}, \sigma' \rangle}
\end{equation}

If the proposed record belongs to a different tenant, PostgreSQL rejects the operation:
\begin{equation}
\frac{\tau \in \mathcal{T} \quad r.\texttt{tenant\_id} \neq \tau}{\langle \mathcal{Q}_{\mathit{write}}(T, r), \sigma, \tau \rangle \to \langle \text{error}(42501), \sigma \rangle}
\end{equation}
Here, error code \texttt{42501} indicates insufficient privilege.

\subsection{Formal Security Properties}
The architecture is designed to maintain five core security properties, formalized under the operational semantics:

\noindent \textbf{Property 1: Strict Non-Interference Between Tenant Contexts.} For any two distinct tenant identifiers $t_A, t_B \in \mathcal{T}$ ($t_A \neq t_B$), and any query $\mathcal{Q}$ executed under tenant context $t_A$, the result set $\mathcal{R}$ must satisfy:
\begin{equation}
\forall r \in \mathcal{R}, \quad r.\texttt{tenant\_id} \neq t_B
\end{equation}
A query executed under context $t_A$ cannot return records belonging to tenant $t_B$ \cite{goguen1982}.

\noindent \textbf{Property 2: Fail-Closed Default.} If a database query executes when the session context is uninitialized ($\tau = \emptyset$), the visibility operator evaluates to the empty set:
\begin{equation}
\Pi_{\emptyset}(\sigma(T)) = \emptyset
\end{equation}
No tenant data is visible unless an authenticated context has been explicitly established.

\noindent \textbf{Property 3: Connection Sanitization Invariant.} When a physical connection $C_i$ is released back to the connection pool at the end of a transaction, its associated tenant context is purged:
\begin{equation}
\tau(C_i) \to \emptyset
\end{equation}
A subsequent transaction borrowing connection $C_i$ begins with an uninitialized context ($\tau = \emptyset$) until explicitly rebound.

\noindent \textbf{Property 4: Audit Trail Immutability.} Every security-relevant event produces an audit record $a = (\mathit{ts}, \tau, u, \mathit{act}, \mathit{res})$ in table $\sigma(\mathit{Audit})$. The system enforces an append-only rule:
\begin{equation}
\forall \sigma \to \sigma', \quad \sigma(\mathit{Audit}) \subseteq \sigma'(\mathit{Audit})
\end{equation}
Audit records cannot be modified or deleted through application roles.

\noindent \textbf{Property 5: Uniform Anti-Enumeration Responses.} When a user belonging to tenant $t_A$ requests an entity with identifier $e_{\mathit{id}}$ that belongs to tenant $t_B$, the application responds with:
\begin{equation}
\text{Response}(e_{\mathit{id}}) = \text{HTTP 404 Not Found}
\end{equation}
The system returns identical responses whether an entity exists in another tenant or does not exist at all, preventing IDOR enumeration attacks.

\subsection{Inductive Proof of Non-Interference under Connection Reuse}
We provide an inductive proof to examine non-interference when a single physical database connection is reused across a sequence of $m$ transactions.

\noindent \textbf{Theorem 1:} For any sequence of $m$ transactions $\langle tx_1, tx_2, \dots, tx_m \rangle$ executed sequentially on physical connection $C$, where each transaction $tx_i$ is associated with tenant $\tau_i \in \mathcal{T}$, no transaction $tx_k$ ($1 \le k \le m$) can observe records belonging to tenant $\tau_j$ ($\tau_j \neq \tau_k$) for any $j \neq k$.

\noindent \textit{Proof by Induction on $m$:}

\textbf{Base Case ($m = 1$):} Transaction $tx_1$ begins on connection $C$ with $\tau = \emptyset$. The transaction manager sets \texttt{autoCommit = false} and executes:
\begin{lstlisting}[language=SQL]
SELECT set_config('app.tenant_id', t1, true);
\end{lstlisting}
Because \texttt{is\_local = true}, the setting is scoped strictly to $tx_1$. PostgreSQL applies the RLS visibility operator:
\begin{equation}
\Pi_{\tau_1}(\sigma(T)) = \{ r \in \sigma(T) \mid r.\texttt{tenant\_id} = \tau_1 \}
\end{equation}
No record with $r.\texttt{tenant\_id} \neq \tau_1$ satisfies the policy. At transaction completion (\texttt{COMMIT} or \texttt{ROLLBACK}), PostgreSQL clears all transaction-local settings. The connection state returns to $\tau = \emptyset$. Non-interference holds for $m = 1$.

\textbf{Inductive Hypothesis:} Assume Theorem 1 holds for any sequence of $k$ transactions ($m = k$). That is, no transaction $tx_i$ ($1 \le i \le k$) observes records belonging to any other tenant, and at the end of transaction $tx_k$, the connection state satisfies $\tau(C) = \emptyset$.

\textbf{Inductive Step ($m = k + 1$):} Transaction $tx_{k+1}$ begins on connection $C$. By the induction hypothesis, connection $C$ arrives from transaction $tx_k$ with $\tau(C) = \emptyset$. If $tx_{k+1}$ executes queries without establishing context, Property 2 applies: $\Pi_\emptyset(\sigma(T)) = \emptyset$, and zero rows are returned. When $tx_{k+1}$ establishes context $\tau_{k+1}$, the interceptor executes:
\begin{lstlisting}[language=SQL]
SELECT set_config('app.tenant_id', tk+1, true);
\end{lstlisting}
The RLS visibility operator becomes $\Pi_{\tau_{k+1}}(\sigma(T))$. For any record $r$ belonging to a previous tenant $\tau_j$ ($j \le k$), since $\tau_j \neq \tau_{k+1}$, the policy predicate evaluates to false. Upon completion of $tx_{k+1}$, the transaction boundary purges the setting, restoring $\tau(C) = \emptyset$. By mathematical induction, Theorem 1 holds for all $m \ge 1$. $\blacksquare$

\subsection{Side-Channel Vectors and Practical Safeguards}
In shared-schema databases, side-channel leakage can occur even when direct row access is prevented. NexusOps addresses three practical side channels:
\begin{enumerate}
\item \textbf{Unique Constraint Enumeration:} If a column such as \texttt{email} has a global uniqueness constraint, an attacker in tenant $T_A$ could determine whether an email exists in tenant $T_B$ by attempting to insert a duplicate record and observing a unique-key violation. NexusOps scopes all uniqueness constraints to include the tenant identifier:
\begin{lstlisting}[language=SQL]
UNIQUE (tenant_id, email)
\end{lstlisting}
Duplicate values can exist across distinct tenants without conflict, preventing cross-tenant existence probing.
\item \textbf{Shared Cache Bleeding:} When caching query results in Redis, cache keys must include the tenant identifier. NexusOps prefixes all cache keys with the tenant context:
\begin{lstlisting}
tenant:{tenant_id}:{entity}:{id}
\end{lstlisting}
This prevents cache hits from crossing tenant boundaries.
\item \textbf{Response Timing Consistency:} Error responses for nonexistent entities and forbidden cross-tenant entities both return HTTP 404 with identical payloads, avoiding timing differentials that could reveal foreign entity existence.
\end{enumerate}

\section{System Architecture and Implementation}
\label{sec:architecture}

NexusOps is implemented as a modular monolithic application using Spring Boot 4 and Java 25. PostgreSQL 17 is used for relational data storage, while Redis 7 handles caching and token-revocation data (Fig. \ref{fig:arch}).

The decision to use a modular monolith instead of a distributed microservices architecture was deliberate. A microservices-based design can introduce additional complexity through distributed transactions, two-phase commit (2PC), network communication, and synchronization across multiple databases \cite{dragoni2017}. By keeping the functional domains within a single application boundary, NexusOps can maintain ACID transactions across related business operations and append-only audit records without requiring distributed coordination \cite{richardson2018, newman2019}.

The application is divided into separate Java packages according to their responsibilities. These include Identity and Tenancy, Authorization and RBAC \cite{sandhu1996}, Directory Services (Users, Organizations, and Items), and the main operational modules, such as CRM, Pipelines, Invoices, and Ledgers. Spring Modulith is used to maintain these module boundaries. It checks package-level dependencies and identifies violations of the defined internal structure during the build process.

All 16 domain tables containing tenant-owned data follow a consistent RLS configuration, as illustrated in Fig. \ref{fig:schema_er}. A shared security kernel provides the tenant context, tenant-aware data source, common entity mapping, database-role verification, and scoped context propagation used by the application modules.

\subsection{Token Authentication and Context Extraction}
NexusOps uses JSON Web Tokens (JWTs) for request authentication. Each access token has a validity period of 15 minutes and is signed using RS256 asymmetric cryptography \cite{jones2015}. The system also issues an HTTP-only rotating refresh token, following the OAuth recommendations referenced in \cite{lodderstedt2025}.

The active tenant identifier is stored in a private JWT claim named \texttt{tid}. To support immediate account suspension and subscription cancellation, the API gateway checks token identifiers against a revocation set maintained in Redis during sensitive state-changing operations.

When an HTTP request reaches the application, a perimeter filter validates the token signature and extracts the \texttt{tid} claim. It then creates an immutable \texttt{TenantContext} representing the authenticated tenant. The gateway deliberately ignores client-controlled sources such as headers (\texttt{X-Tenant-Slug}), form parameters, and tenant identifiers supplied through request payloads, preventing clients from changing their effective tenant simply by modifying request data.

If a request does not contain valid authentication credentials, the tenant context remains empty: $\tau = \emptyset$. For synchronous requests, the application maintains the context within the request execution flow. Asynchronous operations and Java 25 virtual threads use custom context-propagation decorators together with \texttt{ScopedValue} bindings to prevent tenant information from being unintentionally carried into unrelated tasks.

\subsection{Virtual Threads and Scoped Context Propagation}
Modern Java runtimes use virtual threads to support a large number of concurrent tasks without requiring a separate operating-system thread for every request. Although this improves the ability to handle concurrent workloads, it also introduces challenges when request-specific information is stored using traditional thread-local mechanisms.

Under the conventional thread-per-request model, developers commonly use \texttt{ThreadLocal} variables to store information such as the authenticated tenant identifier. This approach works reasonably well when a single operating-system thread handles a request from beginning to end.

Virtual threads change this execution model. They can be suspended and resumed on different carrier threads, while asynchronous executors may also reuse worker threads for unrelated tasks. Using \texttt{InheritableThreadLocal} can introduce further problems because mutable references may be propagated between tasks. If tenant context is not managed carefully, information associated with one request may become visible to another execution context.

NexusOps uses Java 25 \texttt{ScopedValue} primitives together with a custom \texttt{TenantAwareTaskDecorator} to manage this context:
\begin{lstlisting}[language=Java]
ScopedValue.where(TENANT_SCOPE, tenantId)
    .run(() -> executor.execute(task));
\end{lstlisting}
A scoped value provides a bounded and immutable binding. Once the tenant identifier is established at the request boundary, downstream code cannot replace the active value within that scope. The binding is also removed automatically when execution leaves the enclosing scope, rather than relying entirely on developers to write and maintain cleanup logic in \texttt{finally} blocks.

This approach also fits the execution model of virtual threads. When a virtual thread blocks during an operation such as socket I/O, the JVM can detach it from its carrier thread and later resume it on another available carrier. Because the scoped context belongs to the virtual thread's execution scope rather than the carrier thread, the tenant identifier remains associated with the logical task. This design helps prevent tenant-context contamination when multiple virtual threads share the same underlying operating-system resources.

\subsection{Layer 1: Application-Tier ORM Scoping}
The first isolation layer is implemented through Hibernate ORM. Every multi-tenant domain entity in NexusOps extends a common base class that contains the tenant identifier:
\begin{lstlisting}[language=Java]
@MappedSuperclass
public abstract class TenantEntity {
  @TenantId
  @Column(name = "tenant_id", nullable = false, updatable = false)
  private UUID tenantId;
}
\end{lstlisting}
Hibernate's multi-tenancy support uses a registered \texttt{CurrentTenantIdentifierResolver} to obtain the active tenant identifier \cite{hibernate2025}. When preparing JPA queries, Hibernate automatically injects \texttt{AND tenant\_id = :currentTenant} into generated SQL. Inaccessible records return HTTP 404 responses.

However, ORM-level filtering has an important limitation. Hibernate can only modify queries that pass through its entity lifecycle and query compiler. Native SQL statements, raw JDBC operations, bulk updates, and database reporting queries can bypass Hibernate's filtering logic. If an application relied only on ORM-level controls, a developer omitting a tenant filter in a native SQL query could unintentionally expose or modify records across tenant boundaries. As a result, application-tier filtering cannot be treated as the only boundary; database-level enforcement remains essential.

\subsection{Layer 2: Forced Database Row-Level Security}
The second isolation layer is enforced directly by PostgreSQL. To ensure that queries bypassing Hibernate are restricted, every tenant-owned table enables and forces Row-Level Security:
\begin{lstlisting}[language=SQL]
ALTER TABLE <tbl> ENABLE ROW LEVEL SECURITY;
ALTER TABLE <tbl> FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON <tbl> FOR ALL TO nexusops_app
  USING (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid);
\end{lstlisting}
The policy applies to both read and write operations. The \texttt{USING} condition determines which existing rows are visible to queries, while \texttt{WITH CHECK} restricts rows inserted or modified by write operations.

\textbf{Policy Structure and Platform Roles:} The policy is created as a permissive rule for runtime role \texttt{nexusops\_app}. Certain internal operations, such as creating new organizations or performing cross-tenant billing aggregations, require administrative access. NexusOps separates these operational tasks from ordinary application traffic by assigning them to a dedicated database user, \texttt{nexusops\_platform}, operating under separate audit logging.

\textbf{Database Roles and Migration Privileges:} Schema migrations are executed during application deployment using \texttt{nexusops\_owner}. This role possesses table ownership privileges and the \texttt{BYPASSRLS} attribute required to create and alter database objects. The production application, by contrast, connects using the restricted runtime role \texttt{nexusops\_app}, which holds \texttt{NOBYPASSRLS} and cannot alter table structures or create new database objects \cite{postgresql17docs}. Audit tables are protected via database triggers blocking unauthorized \texttt{UPDATE} and \texttt{DELETE}, with \texttt{TRUNCATE} revoked outright (Property 4).

\textbf{Handling Missing or Malformed Tenant Identifiers:} The policy uses \texttt{NULLIF} around \texttt{current\_setting('app.tenant\_id', true)}. Missing settings evaluate to \texttt{NULL}, failing closed under SQL three-valued logic. Invalid UUID strings trigger PostgreSQL error \texttt{22P02}, aborting the transaction.

\subsection{Connection Sanitization across Recycled Pools}
Production application servers commonly use connection pools such as HikariCP to manage database connections efficiently. Rather than opening a new physical connection for each incoming request, the pool reuses a fixed set of database connections across many transactions. If session settings are executed in autocommit mode, settings clear immediately upon checkout.

NexusOps addresses this issue by delaying tenant binding until the database transaction is established. The connection lifecycle follows five distinct operational states (Fig. \ref{fig:state_machine}):
\begin{enumerate}
\item \textbf{S0 – Pool Idle:} HikariCP holds an idle connection with no active tenant context ($\tau = \emptyset$).
\item \textbf{S1 – Transaction Initiated:} The platform transaction manager obtains a connection from the pool and sets \texttt{autoCommit = false}.
\item \textbf{S2 – Context Bound:} Before the first repository query executes, the interceptor sets \texttt{app.tenant\_id} locally for the active transaction.
\item \textbf{S3 – DML Scoped:} Application queries execute with both Hibernate filtering and PostgreSQL RLS active.
\item \textbf{S4 – Purge and Sanitize:} When the transaction completes through \texttt{COMMIT} or \texttt{ROLLBACK}, PostgreSQL removes the transaction-local setting before the connection is returned to the pool.
\end{enumerate}

\begin{lstlisting}[language=Java,caption={Transaction Connection Interceptor}]
public class TenantConnectionInterceptor implements ConnectionProvider {
  @Override
  public Connection getConnection() throws SQLException {
    Connection connection = dataSource.getConnection();
    if (!TransactionSynchronizationManager.isActualTransactionActive()) {
      return connection;
    }
    String currentTenant = TenantContextHolder.getTenantId();
    if (currentTenant != null) {
      try (PreparedStatement stmt = connection.prepareStatement(
          "SELECT set_config('app.tenant_id', ?, true)")) {
        stmt.setString(1, currentTenant);
        stmt.execute();
      }
    }
    return connection;
  }
}
\end{lstlisting}
The interceptor first obtains a connection from the data source and checks whether a Spring transaction is active. When a transaction is active and a tenant identifier is available, the interceptor executes a parameterized \texttt{set\_config()} statement. The third argument is set to \texttt{true}, making the session variable transaction-local.

The tenant context is therefore established within the transaction boundary rather than at the connection level. When the transaction finishes, PostgreSQL automatically clears the variable, ensuring that the connection returns to the pool in a clean state. This transaction-scoped binding introduces approximately $0.038$ ms dispatch overhead per transaction boundary.

\section{Automated Guardrails Against Policy Erosion}
\label{sec:guardrails}

Security controls may be correctly implemented when an application is first developed, but that does not guarantee they will remain effective as the system changes. New tables, reporting views, database functions, and migration scripts can introduce gaps in tenant isolation if existing security requirements are not checked consistently.

In a fast-moving development environment, relying only on code reviews and developer awareness is not sufficient. A migration that creates a new table without enabling RLS, for example, may introduce an unprotected data path without producing an obvious application error.

To reduce this risk, NexusOps uses three automated guardrails operating across the development and deployment lifecycle: build-time catalog auditing, policy mutation testing, and runtime database-role verification.

\subsection{Build-Time Catalog Auditing and AST Verification}
NexusOps uses an integration test named \texttt{RlsCoverageIT} to examine the PostgreSQL system catalog during the Maven build. The test starts an ephemeral PostgreSQL database through Testcontainers, applies current migrations, and checks the resulting security configuration across \texttt{pg\_class}, \texttt{pg\_namespace}, \texttt{pg\_policy}, and \texttt{pg\_views}:
\begin{lstlisting}[language=SQL]
SELECT c.relname, p.polname
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
LEFT JOIN pg_policy p ON p.polrelid = c.oid
WHERE n.nspname = 'public'
  AND c.relkind IN ('r', 'p')
  AND c.relname NOT IN ('permissions', 'subscription_plans')
  AND (NOT c.relrowsecurity
       OR NOT c.relforcerowsecurity
       OR p.polname IS NULL
       OR p.polcmd != '*'
       OR NOT p.polpermissive
       OR pg_get_expr(p.polqual, p.polrelid)
          IS DISTINCT FROM :canonicalExpr
       OR pg_get_expr(p.polwithcheck, p.polrelid)
          IS DISTINCT FROM :canonicalExpr
       OR (SELECT count(*) FROM pg_policy WHERE polrelid = c.oid) != 1);
\end{lstlisting}
where \texttt{:canonicalExpr} contains the canonical tenant-isolation predicate:
\begin{lstlisting}[language=SQL]
(tenant_id = (NULLIF(
  current_setting('app.tenant_id'::text, true),
  ''::text))::uuid)
\end{lstlisting}
PostgreSQL provides the \texttt{pg\_get\_expr()} function to convert stored expression trees into readable SQL expressions. NexusOps compares these expressions with the canonical predicate using \texttt{IS DISTINCT FROM}. This comparison helps identify differences in the stored policy expressions, including cases where an expected expression is missing or evaluates to NULL.

The build-time audit enforces four main requirements:
\begin{enumerate}
\item \textbf{RLS and FORCE RLS must both be enabled:} Every tenant-owned table must have both \texttt{relrowsecurity} and \texttt{relforcerowsecurity} enabled. Without FORCE RLS, the table owner may bypass row-level restrictions.
\item \textbf{Read and write predicates must match the canonical expression:} The policy's \texttt{polqual} and \texttt{polwithcheck} expressions must follow the expected tenant condition.
\item \textbf{Policy cardinality must remain controlled:} Each relation must have exactly one permissive policy. This prevents an additional permissive policy from unintentionally expanding access through PostgreSQL's OR-based policy combination.
\item \textbf{Views must preserve caller security context:} A database view that accesses tenant-owned data must use \texttt{security\_invoker = true}, so that access is evaluated using the invoking user's permissions and RLS context.
\end{enumerate}
If any of these requirements is violated, the catalog audit reports the affected relation and causes the build to fail.

\subsection{Policy Mutation Analysis Across Four Operational Quadrants}
A catalog check may identify missing or incorrect policy configurations, but its effectiveness also needs to be tested against deliberate failures. To evaluate this, NexusOps uses a dedicated mutation-testing script named \texttt{verify\_policy\_guard.sh}. The script introduces 16 deliberately incorrect schema configurations into a temporary relation called \texttt{probe\_table}, grouped into four operational categories:

\textbf{1) Quadrant I: Missing Flags and Exemption Holes:} Mutant 1 (Unprotected Table) creates a table without enabling RLS. Mutant 2 (Unforced Owner Bypass) enables RLS but omits FORCE RLS, allowing the table owner to bypass the policy. Mutant 5 (Missing Write Check) defines a valid \texttt{USING} condition but omits \texttt{WITH CHECK}. Mutant 8 (Maintenance Role Leak) simulates administrative operations against unforced tables. All 4 configuration failures are detected by the catalog checks.

\textbf{2) Quadrant II: Predicate Distortion and Permissive Injections:} Mutant 3 (Permissive Write Hole) sets \texttt{WITH CHECK (true)}, removing write restrictions. Mutant 4 (Permissive Read Hole) sets \texttt{USING (true)}, allowing unrestricted row visibility. Mutant 7 (Column Misdirection) filters \texttt{created\_by} instead of \texttt{tenant\_id}. Mutant 8b omits \texttt{NULLIF}, risking exceptions on uninitialized settings. Mutants 13 and 14 add tautological \texttt{OR true} injections. Mutant 15 places a hardcoded UUID literal into the policy. Mutant 16 changes the expected session variable name (GUC namespace drift). The AST comparison detects all 7 deviations from the canonical expression.

\textbf{3) Quadrant III: Role Misconfigurations and Restrictive Deadlocks:} Mutant 6 (Disjunctive Policy Stacking) adds a second permissive policy, expanding access through OR-combination. Mutant 9 (Orphan Restrictive Rule) adds a restrictive policy without an appropriate permissive policy, causing denial of service. Mutants 11 and 12 apply policies only to selected operations (SELECT or INSERT) rather than covering all commands (\texttt{*}). The audit checks catch all 4 misconfigurations.

\textbf{4) Quadrant IV: Unsafe Relational Views:} Mutant 10 (Defective View Invoker) creates an analytics view over tenant-owned data without setting \texttt{security\_invoker = true}. Under default view behavior, access is evaluated using the creator's permissions, undermining RLS. NexusOps flags this via \texttt{pg\_views}.

Across the complete mutation suite, the reported guardrail detection result was 16 out of 16 mutations blocked, corresponding to a 100\% detection rate within tested scenarios.

\subsection{Runtime Startup Role Verification}
Correct database policies are not enough if the application connects using an account with excessive privileges. A runtime account with superuser privileges or the \texttt{BYPASSRLS} attribute can bypass the intended row-level restrictions.

To reduce this risk, NexusOps includes a startup verification component named \texttt{DatabaseRoleGuard}. The component runs during Spring's application bootstrap sequence, before the service begins accepting HTTP requests. It checks the privileges associated with the active database connection and stops application startup if the \texttt{nexusops\_app} role possesses superuser privileges (\texttt{rolsuper}), RLS-bypass attributes (\texttt{rolbypassrls}), table ownership, or schema \texttt{CREATE} permissions. The baseline Flyway migration also revokes \texttt{PUBLIC} execution privileges on shared functions, closing untrusted \texttt{SECURITY DEFINER} escalation pathways.

\section{Empirical Security Evaluation}
\label{sec:sec_eval}

A security design may appear sound on paper, but its effectiveness becomes clearer when the system is exposed to realistic implementation mistakes. Developers may overlook an annotation, introduce an unsafe database query, or deploy a migration with an incomplete security policy. These situations can create weaknesses even when the overall architecture follows a defense-in-depth approach.

To examine how NexusOps responds to such failures, we defined 16 fault scenarios covering application code, database configuration, connection management, and related infrastructure. The results are summarized in Table \ref{tab:fault_injection}.

\subsection{Fault-Injection Mutation Testing}
Several scenarios demonstrate the importance of enforcing tenant isolation at more than one layer. For example, omitting the \texttt{@TenantId} annotation from a newly added JPA entity (Scenario 1) or executing a native SQL query without a tenant predicate (Scenario 2) can bypass the application's ORM-level filtering. In both cases, PostgreSQL RLS still restricts the returned rows to the tenant associated with the active transaction.

The same principle applies to connection reuse. A connection that previously served another tenant may retain an incorrect context if its state is not reset properly. Scenario 4 examines this condition. The database-level protection prevents access to rows belonging to the previous tenant, while the automated test suite checks that the connection lifecycle behaves as expected.

\subsection{Concurrency Leakage Benchmark and Positive Controls}
Unit tests are useful for checking expected application behavior, but they may not reveal problems that occur only under concurrent execution. In a multi-tenant application, connection reuse, asynchronous task handoffs, and rapid changes in tenant context can introduce temporary state inconsistencies. Such failures are particularly important to investigate when many requests share a limited database connection pool.

We therefore evaluated NexusOps using a concurrent workload designed to exercise tenant-context switching under sustained request activity. The test generated 1,000,000 randomized cross-tenant requests using 100 concurrent worker threads sharing a HikariCP pool of 32 database connections. Across the test, the workload produced 940,000 tenant-context transitions involving 100 organizations and 16 business tables.

\textbf{Canary Token Verification Harness:} Each persisted record included an encrypted canary token in the format:
\begin{lstlisting}
canary_{tenant_id}_{uuid}
\end{lstlisting}
After receiving a query result, each test client checked whether the token belonged to the tenant identified by its assigned JWT claim. This provided a direct way to identify cross-tenant records in the response. If even one record carried a token associated with another tenant, the test harness immediately stopped the run.

\textbf{Positive Controls and Harness Verification:} A test harness must be capable of detecting a failure before its results can be trusted. To verify this, we performed three positive-control experiments:
\begin{enumerate}
\item First, Hibernate tenant filters were deliberately disabled while PostgreSQL RLS remained active. Across 10,000 probe requests, the database policy blocked every cross-tenant access attempt.
\item Second, RLS was disabled at the database layer while Hibernate filters remained active. In this configuration, the ORM layer maintained tenant isolation, producing zero observed leaks.
\item Finally, both protections were disabled simultaneously on a dedicated test endpoint. Under this condition, the canary-token harness detected all resulting cross-tenant leaks in less than 12 ms.
\end{enumerate}
These controls demonstrate that the harness distinguished between protected and deliberately unprotected configurations rather than simply reporting successful test execution.

\textbf{Statistical Bound Using the Rule of Three:} During the complete concurrency experiment, the harness observed zero cross-tenant record leaks across one million requests.

A zero-event result does not establish that the probability of leakage is exactly zero. Instead, the Hanley--Lippman-Hand Rule of Three \cite{hanley1983} provides an approximate upper confidence bound for the event probability when no failures are observed. For $N$ independent observations with zero observed events, the approximate 95\% upper bound is:
\begin{equation}
p_{95\%} < \frac{3}{N}
\end{equation}
Substituting the observed number of requests:
\begin{equation}
p_{95\%} < \frac{3}{1,000,000} = 3 \times 10^{-6} \quad (0.0003\%)
\end{equation}
This corresponds to an approximate upper bound of 0.0003\% for the evaluated test conditions.

The result provides empirical evidence that transaction-boundary resets, connection sanitization, and tenant-context propagation operated correctly under the tested workload. However, it should be interpreted within the limits of the experiment. It does not establish a universal guarantee against untested query paths, compromised tenant credentials, lower-level database vulnerabilities, or other conditions outside the test environment.

\section{Experimental Performance Evaluation}
\label{sec:evaluation}

\subsection{Experimental Methodology}
Evaluating the performance of a defense-in-depth architecture requires looking at two separate sources of overhead. The first comes from the additional network operation needed to set the tenant session variable. The second comes from PostgreSQL evaluating row-level security predicates during query execution. Measuring both together would make it difficult to determine how much overhead is introduced by each mechanism.

We therefore designed the benchmark around PostgreSQL 17.11 and compared three configurations under controlled conditions:
\begin{enumerate}
\item \textbf{Filter-Only Baseline (ORM Tier):} This configuration used shared database tables without enabling database-level RLS. Tenant filtering was performed by the application through generated SQL conditions such as \texttt{WHERE tenant\_id = ?}. No \texttt{set\_config()} call was required.
\item \textbf{Sanitized Filtering (Protocol Baseline):} This configuration retained application-level tenant filtering and added session-variable assignment when a connection was checked out. Database RLS remained disabled. This allowed us to measure the additional client-server communication required to establish the tenant context.
\item \textbf{Dual-Layer (PostgreSQL Forced RLS + Filter):} This configuration enabled both ORM filtering and forced database-level RLS. The tenant context was assigned to the database session, and PostgreSQL evaluated the corresponding security predicates while executing the same application queries.
\end{enumerate}

Using \texttt{pgbench}, we evaluated four common database operations: single-entity Point Lookups, keyset-paginated Paged Lists of 20 sorted rows, aggregate Tenant Counts across all tenant records, and Point Inserts evaluating the RLS \texttt{WITH CHECK} policy condition.

The evaluation dataset contained 1,000,000 records distributed evenly across 100 organizations (10,000 records per organization). Each record included a 64-bit integer primary key, a 128-bit UUID tenant identifier, and standard business attributes, backed by a composite index on \texttt{(tenant\_id, name)}.

All experiments ran on a dedicated Linux host (kernel 6.6, AMD EPYC 7763, 10 vCPUs, 16 GB RAM, NVMe SSD storage) running PostgreSQL 17.11 with \texttt{shared\_buffers = 4GB}, \texttt{work\_mem = 64MB}, \texttt{max\_connections = 200}, and \texttt{synchronous\_commit = off}. Each trial used 8 concurrent clients across 4 worker threads for 2 seconds after an unmeasured warm-up period. Tables were truncated, reseeded, and vacuumed between cycles. Following established benchmarking guidelines \cite{georges2007, kalibera2013, mytkowicz2009}, we gathered $n = 30$ randomized paired trials for each workload.

\subsection{Throughput, Latency, and Statistical Equivalence}
Table \ref{tab:benchmarks} summarizes the throughput and latency measurements obtained across the 30 paired trials. Mean transaction latency was derived from transaction rate ($L = c/\text{tps}$), while the 99th-percentile tail latency was calculated directly from transaction logs (\texttt{pgbench -l}). Figure \ref{fig:latency_comp} presents the corresponding mean and tail-latency comparisons.

\textbf{Separating Protocol and Database Overhead:} The results show that the measured performance difference has two main sources. The first is the additional network round-trip required to execute \texttt{set\_config()}. For short transactions involving a single database statement, this operation adds approximately $0.17$--$0.44$ ms. Since the Filter-Only Baseline does not perform this operation, the Dual-Layer configuration achieves throughput ratios between $0.726$ and $0.907$ relative to that baseline across the four microbenchmarks.

However, this comparison includes both session-configuration and RLS costs. To isolate the database-level contribution, we compared Dual-Layer RLS against the Filter + Sanitized configuration. Both configurations perform the same context-setting operation, so the remaining difference primarily reflects the additional work performed by PostgreSQL's RLS enforcement. The point-insert workload showed the smallest difference: its throughput ratio was $0.977$, with a 95\% confidence interval of $[0.947, 1.007]$, corresponding to approximately $2.3\%$ overhead. Read workloads showed differences of approximately $6.3\%$ to $8.8\%$ relative to the sanitized baseline.

\textbf{Statistical Equivalence Testing Using TOST:} A statistically significant difference does not necessarily mean that two configurations are operationally different. For this reason, we used Two One-Sided Tests (TOST) \cite{schuirmann1987, lakens2018} to examine whether Dual-Layer RLS remained within a predefined performance-equivalence interval of $\pm 10\%$ relative to the sanitized baseline ($\theta_L = 0.90, \theta_U = 1.10$). For each paired run, the throughput ratio was log-transformed:
\begin{equation}
z_i = \ln\left(\frac{\text{Throughput}_{\text{Dual},i}}{\text{Throughput}_{\text{Sanitized},i}}\right)
\end{equation}
The reported TOST results rejected the null hypothesis of meaningful divergence for Paged List ($p = 2.33 \times 10^{-3}$), Tenant Count ($p = 3.22 \times 10^{-2}$), and Point Insert ($p = 5.55 \times 10^{-6}$). For point inserts, Cohen's $d = -0.98$, and the 95\% confidence interval $[0.947, 1.007]$ crosses 1.0, confirming that write performance remained practically equivalent to the sanitized baseline. Figure \ref{fig:ratio} presents the paired throughput ratios against the baseline alongside a $\pm 5\%$ visual equivalence corridor.

\subsection{Evaluation Under Complex Real-World Workloads}
Typical production workloads involve more than isolated database lookups. Applications frequently execute joins across related tables, serve organizations with very different data volumes, and experience periods of high connection demand. To examine these conditions, we evaluated relational joins, tenant-size skew, and connection-pool saturation (Table \ref{tab:complex_benchmarks}, $n = 30$ paired runs each).

\textbf{Relational Graph Joins and Foreign-Key Pushdown:} Applying RLS to multiple related tables can affect query execution if tenant predicates are evaluated inefficiently during joins. NexusOps uses tenant-qualified foreign keys, such as \texttt{(tenant\_id, order\_id)}, allowing the tenant condition to participate in index-based access to related tables. In the evaluated workloads, PostgreSQL selected Nested Loop Inner Index Scan operations rather than materializing cross-tenant intermediate hash tables. Throughput ratios relative to the Filter-Only Baseline were $0.731$ $[0.712, 0.750]$ for two-table joins (\texttt{orders} $\bowtie$ \texttt{order\_items}) and $0.736$ $[0.720, 0.752]$ for three-table joins ($\bowtie$ \texttt{order\_payments}). The results indicate that the measured throughput ratio remained consistent when join depth increased, provided composite indexes and tenant-qualified relationships were in place.

\textbf{Tenant Skew and Generic Plan Caching:} Real SaaS environments do not distribute records evenly across organizations. We evaluated an 80/20 Pareto-style distribution across 100 organizations: one large organization contained 250,000 records (25\% of the dataset), while smaller organizations contained 500 records each (0.05\%). The measured throughput ratios were $0.719$ $[0.703, 0.734]$ for small tenants ($9,296$ tps) and $0.713$ $[0.701, 0.725]$ for the whale tenant ($9,568$ tps). The composite indexes place \texttt{tenant\_id} at the leading position, keeping B-tree depth at three levels across all tenant sizes with shared-buffer hit rates above 99.8\%. After five executions, PostgreSQL transitioned from custom plans to cached generic plans, evaluating the session variable during scan initialization while retaining leading index-key probing.

\textbf{Connection-Pool Saturation and Queue Latency:} We also examined how the system behaved as active client concurrency increased from 8 to 32 clients against the 32-connection HikariCP pool (Fig. \ref{fig:concurrency_scaling}). At 8 clients, mean transaction latency was $1.05$ ms on the baseline and $1.40$ ms on Dual-Layer RLS; at 32 clients (pool saturation), these values rose to $3.54$ ms and $4.94$ ms (p99 tail latency: $9.59$ ms and $12.50$ ms). Connection-pool contention and network queuing become the primary contributors to latency under saturation, dwarfing the sub-millisecond cost of evaluating RLS predicates. Across the full HTTP stack (Spring Boot, HikariCP, JSON serialization), median request latency was $2.4$ ms and p99 was $6.8$ ms.

\section{Developer Experience and Operational Case Study}
\label{sec:developer_experience}

Security mechanisms that impose excessive operational complexity or cognitive friction often suffer from poor compliance and eventual circumvention. To assess the practical viability of dual-layer tenant isolation, we evaluate developer ergonomics, schema migration workflows, and diagnostic support procedures implemented in NexusOps.

\subsection{Developer Ergonomics and Cognitive Load}
Under a conventional application-only filtering model, developers bear ongoing cognitive responsibility for verifying tenant parameters across every query construct. In contrast, the dual-layer approach establishes tenant isolation as an infrastructural default.

When writing standard domain logic, developers simply extend \texttt{TenantEntity}. The base class encapsulates the \texttt{@TenantId} discriminator, which Hibernate resolves automatically through the registered context resolver. Developers write idiomatic Spring Data repository methods without manually qualifying queries with tenant parameters.

The database layer provides an additional safeguard for queries that do not pass through the normal ORM filtering mechanism. For example, a developer may use \texttt{createNativeQuery()} or Spring Data's \texttt{@Query(nativeQuery = true)} without including the tenant discriminator. In an application-only filtering design, this omission could expose records from other tenants. In NexusOps, forced PostgreSQL RLS applies the active transaction's tenant context to the query and restricts the returned rows.

The same approach is used during database development. If a developer creates a new table through a Flyway migration but forgets to enable and force RLS, the \texttt{RlsCoverageIT} catalog integration test detects the missing policy configuration. The test runs as part of the local CI workflow and fails the build within $4.2$ seconds on a local laptop. \subsection{Zero-Downtime Schema Evolution}
Database schema changes are particularly important in SaaS applications that must remain available throughout the day. NexusOps connects Flyway migrations with automated RLS policy verification. When a new tenant-facing table is added, the migration follows a defined sequence: creating the table with composite primary key \texttt{(tenant\_id, id)}, enabling row-level security via \texttt{ALTER TABLE ... ENABLE ROW LEVEL SECURITY}, applying \texttt{FORCE ROW LEVEL SECURITY}, and creating the canonical tenant policy. Before proceeding to staging, CI/CD starts a fresh PostgreSQL instance via Testcontainers and runs \texttt{RlsCoverageIT}, failing automatically if policy coverage is missing.

\subsection{Segregated Customer Support Workflows}
Diagnostic consoles connect through a dedicated connection pool named \texttt{PlatformAdminDataSource}, using the restricted role \texttt{nexusops\_platform}. Support engineers obtain short-lived 5-minute tokens requiring two-person approval linked to active customer tickets. Every query logs an immutable entry in \texttt{audit\_events} containing operator identity, target organization ID, ticket reference, and the SHA-256 hash of the executed SQL statement.

\section{Discussion and Threats to Validity}
\label{sec:threats}

\textbf{Internal Validity:} Performance experiments ran on dedicated bare-metal hardware with fixed CPU affinity and isolated memory allocations. To limit variations from JVM JIT compilation and buffer priming, we randomized trial order and excluded warm-up runs \cite{georges2007}. Tables were truncated, reseeded, and vacuumed between write cycles to prevent dead-tuple accumulation from affecting subsequent measurements.

\textbf{External Validity:} Production SaaS applications feature complex relationships and skewed customer data distributions. We evaluated joins across up to three relations and 80/20 Pareto distributions (Table \ref{tab:complex_benchmarks}). While deep recursive graph queries or unindexed predicates may lead PostgreSQL to choose different execution plans, enterprise workloads following composite indexing conventions maintain stable index-scan behavior across join hierarchies.

\textbf{Construct Validity and Attacker Capabilities:} The threat model distinguishes vulnerability classes: ORM omissions and native queries are intercepted by RLS; IDOR attempts are blocked at both layers; connection bleeding is prevented via transaction hooks. However, RLS does not protect against arbitrary SQL injection executed under application privileges, as an attacker could invoke \texttt{set\_config()} directly. Parameterized queries and prepared statements remain indispensable.

\textbf{Policy Complexity Considerations:} We evaluated equality policies operating over indexed columns. Policies using subqueries or non-leakproof functions may impede index pushdown, increasing per-row CPU costs. Tenant policies should remain simple and index-aligned.

\section{Limitations and Future Work}
\label{sec:limitations}
Although dual-layer isolation provides strong tenant isolation with low measured overhead, several practical constraints remain.

External transaction poolers such as PgBouncer or Odyssey multiplex connections across clients. Transaction-local settings (\texttt{is\_local = true}) operate cleanly in transaction-pooling mode, but intermediate proxy multiplexing was not directly evaluated in our physical testbed. High-dimensional vector search using \texttt{pgvector} also introduces considerations; applying RLS predicates across HNSW graphs can degrade recall if filtering occurs after traversal rather than during index probing. Per-tenant vector partitioning may offer a more predictable design. In addition, 15-minute JWT lifetimes leave a window where compromised tokens remain active unless revoked via Redis. Finally, our benchmarks evaluate single-node PostgreSQL; distributed architectures (Citus, CockroachDB, Spanner) introduce distributed consensus costs requiring independent evaluation. Future work will investigate multi-region deployments and cryptographically signed session tokens verified within the database engine.

\section{Conclusion}
\label{sec:conclusion}
Relying entirely on developer discipline to enforce tenant isolation across shared-schema SaaS databases creates an ongoing operational risk. A missing tenant filter in a single query can compromise confidential records. NexusOps addresses this challenge by combining application-level ORM filtering with PostgreSQL forced Row-Level Security, providing defense-in-depth against data leakage. Automated catalog verification in CI, startup role checks, and transaction-scoped connection sanitization systematically eliminate configuration drift, connection pool contamination, and privilege escalation.

Our empirical evaluation over 1,000,000 records ($n = 30$ paired trials) demonstrates that database-level forced RLS introduces modest overhead ($2.3\%$ to $8.8\%$ over sanitized baselines), with Two One-Sided Tests confirming statistical equivalence within an operational $\pm 10\%$ corridor. The platform sustains low latency across multi-table joins, skewed tenant distributions, and saturated connection pools. By shifting tenant boundary enforcement from developer discipline to database kernel invariants, dual-layer isolation provides a robust and practical foundation for multi-tenant SaaS systems.
