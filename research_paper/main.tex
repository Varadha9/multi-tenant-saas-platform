\begin{abstract}
Many systems operate using a single-schemas system in order to reduce infrastructure and hosting costs. However, ensuring data isolation between tenants in such systems can be challenging. As data from multiple organisations is stored in the same table, application queries must be designed correctly to ensure isolation. If a query fails to include tenant information, users may be able to view data from other organisations.

In this paper, an investigation of NexusOps was undertaken, an application developed in Spring Boot and Postgres. Two levels of isolation have been applied to ensure tenant data isolation; ORM-based filtering and Row-Level-Security in Postgres. Together these techniques ensure that only records relevant to a particular tenant can be viewed.

The architecture of the system, connection management, security properties and performance of the system was investigated. A transaction scoped connection scheme was introduced to avoid tenant context leaking in a pooled connection. The system was tested in terms of security with automated tests, 16 mutation faults, and performance using 1,000,000 database tuples in Postgres 17. In a concurrency test of 1,000,000 requests with 100 workers, 32 connections and 940,000 tenant context switches, no data leak between tenants was found. Row-Level security in Postgres added overhead to requests of 2.3\%--8.8\% compared to sanitised baselines. Overall, combining ORM filtering and database based security can be useful to provide additional tenant isolation, with acceptable levels of performance overhead.
\end{abstract}

\section{Introduction}
\IEEEPARstart{M}{any} businesses will currently manage business processes using spreadsheets, paper data and messaging applications. For example, managing sales leads, inventory and invoices can all be done using these tools. Managing business data in this manner however can introduce errors in data, inconsistency, and problems in recording accurate information. Studies have shown that many errors occur in spreadsheet based business processes. For example, both Panko \cite{panko1998} and Powell et al. \cite{powell2009} have found frequent errors in operational spreadsheets, leading to inefficiencies in business.

Cloud based SaaS applications can be utilised to increase efficiency of managing business operations and data. However, it is important to consider the cost implications of managing these. Smaller businesses often lack funds to purchase subscriptions for many SaaS services, meaning that providing separate databases or virtual machines for each user is not always feasible for SaaS providers. Many SaaS providers have implemented single-schema systems to address this issue. By having data of multiple organisations stored in the same table within the same database \cite{chong2006, aulbach2008, armbrust2010} efficient use of resources can be made. As a result, hosting costs can be greatly reduced compared to having separate database environments for each tenant \cite{kabbedijk2015}.

\subsection{Security Considerations in Single-Schema Systems}
While single-schema databases are efficient, care must be taken to isolate tenant data. Within the same table, data from multiple organisations is stored. This data is usually differentiated by including a \texttt{tenant\_id} in each record. Therefore, queries must include tenant conditions to ensure that each organisation can only see data relevant to them.

If a query that is intended to return customer data, for example, fails to include a tenant condition in the form of \texttt{WHERE tenant\_id = :current\_tenant}, then if this query has been made in a new endpoint, report, batch process or native SQL statement, by accident, then the database will execute the query, without isolating it to the requested tenant. Depending on the operation, data from other organisations could be exposed, modified or deleted.

This issue relates to common security issues in modern applications. Broken Access Control and Broken Object Level Authorisation (BOLA) \cite{owasp2021, owaspapi2023} are known security risks. In addition, according to the Verizon Data Breach Report, human error in configuration and missing security measures or misusing credentials are significant factors in security incidents \cite{verizon2023}. In addition, IBM has reported significant financial impacts from data breaches in enterprises \cite{ibm2023}. In SaaS systems, data leakage between tenants can cause significant damage to the trust customers hold in the business, disrupt business continuity, and cause problems meeting regulation requirements.

\subsection{Defence in Depth}
Following the principle of defence in depth \cite{saltzer1975} it is important to ensure that critical security features are not reliant upon a single protection mechanism. In multi-tenant systems, implementing two levels of tenant isolation is vital.

Using ORM frameworks (such as Hibernate) in the application tier allows tenant conditions to be automatically added to queries made to the database. This decreases the burden on developers to manually include tenant isolation in all operations. However, there are situations in which ORMs will not apply tenant filtering. Queries written in native SQL and queries made directly in JDBC may bypass the ORM.

PostgreSQL allows Row Level Security to be applied to data. If appropriate policies are in place, tenant conditions will be applied at the database level. Even if no tenant condition is applied in application queries, data can still be isolated between tenants in this method \cite{aws2020, postgresql17docs, postgresql17notes}.

However, there are considerations to be made when implementing RLS at the database level. Firstly, performance in queries and applications may be impacted. Developers may be concerned that applying policies in queries may cause delays in query planning, indexing and speed. Second, connection pooling means that a physical connection can be reused in multiple requests. Care must be taken in managing tenant specific data in sessions to ensure that different requests do not interfere. Additionally, migrations to new versions of database schemas may cause issues, as newly created tables may not have appropriate security policies set.

It is therefore important to consider both the security benefits and the behavior of combining ORM and RLS during normal operation.

\subsection{Contribution}
This paper investigates the design and implementation of NexusOps, a business operations management system built using Spring Boot and Postgres. This system employs two levels of tenant data isolation, by using tenant filtering in the application and Row Level Security in Postgres.

Contributions include:
\begin{enumerate}
\item Transaction scoped connection management, to ensure tenant information is tied to a transactions, and cleaned up appropriately in pooled connections.
\item Formal operational semantics, and an inductive proof to examine that no interference occurs between tenants in reused connections.
\item Automated validation of schema, to identify incomplete or incorrect RLS policies in schema changes and application startup, by analysing policies and expressions in databases.
\item Security validation. Validation is performed using canary tokens, positive control, and mutation testing with 16 mutations, to determine whether any implementation faults could lead to data leakage between tenants.
\item Engineering and Maintainability validation. Investigation into practical considerations of the implementation. This includes ease of engineering for developers, zero downtime migrations for schema changes, and support for diagnosing tenant issues.
\item Performance validation. Performance of database row level security in different scenarios in Postgres 17. Paired benchmark runs have been performed and equivalence testing to determine effects on performance.
\end{enumerate}

\section{Background}
\label{sec:background}

Multi tenancy has been widely researched in databases and enterprise software. With widespread adoption of cloud computing, methods of sharing computing and database resources between multiple organisations have been investigated \cite{armbrust2010, bezemer2010}.

\subsection{Multi Tenancy Design}
There are 3 general models for multi tenancy in databases: 1 per tenant, 1 per schema and single-schemas \cite{chong2006, kabbedijk2015}.

1 per tenant databases give complete separation between tenants, and are simple to backup, migrate and allocate resources for each customer. However, many database instances or files must be maintained which increases infrastructure costs and administrative complexity as the number of organisations increases \cite{jacobs2007}.

1 per schema databases group multiple customers in one database instance. Each organisation has different namespaces or schemas. While less overhead is caused at the instance level than in the 1 per tenant model, hundreds or thousands of schemas can cause performance issues for database management systems in migration, lookup and meta data operations \cite{weissman2009}.

Single schema databases include data from all organisations in the same group of tables. Each record is associated with a tenant by including a tenant identifier (\texttt{tenant\_id}) as a column \cite{aulbach2008, guo2007}. This design results in very efficient resource usage, and so is commonly used in SaaS for enterprises \cite{krebs2012, schiller2011}. However, as data from multiple tenants is in the same place, application code and queries must ensure that data cannot be accessed by other tenants \cite{narasayya2022}.

\subsection{Row Level Filtering in Database}
Declarative RLS was introduced in version 9.5 of PostgreSQL. Integration with the Query Planner was improved in version 17 \cite{postgresql17docs, postgresql17notes}. When RLS is enabled on a table, queries sent to that table will be modified to include conditions from the relevant security policy. As a result, regardless of whether there is a tenant filter in the query or not, the security policy condition will be applied in the query plan.

Query modification in RLS builds on previous ideas in early relational databases \cite{stonebraker1974}. In these systems, access controls were enforced by modifying queries before execution. Modern systems allow similar functionality. Oracle provides Virtual Private Databases (VPD), Microsoft SQL Server provides Row level security, and MySQL provides filtering via views. All allow security conditions to be enforced by the database rather than completely relying on application code.

Within application development, tenant filtering is often performed within ORM systems. For example, in Hibernate, tenant conditions can be automatically added to SQL queries \cite{hibernate2025}. However, queries outside of ORM, such as native SQL queries, reports and direct connections, will not have tenant conditions applied.

\subsection{Multi Tenancy and Role Based Permissions}
Generally, in multi tenant systems, tenant isolation and role based permissions are separated \cite{sandhu1996, ferraiolo2001}.

Tenant isolation ensures that only data from the correct organisation is accessed. It creates separation between customers, and is usually considered before considering individual user permissions. In NexusOps, each tenant is identified using a constant \texttt{tenant\_id}. This remains associated with the request throughout its life.

Role based permissions ensure that users can perform specific actions within their organisation. Within NexusOps, users are assigned a role to determine what permissions they have. These roles include \texttt{OWNER}, \texttt{ADMIN}, \texttt{MEMBER} and \texttt{VIEWER}. These roles determine what features users have available in the application, for example creating invoices and viewing reports. However, these roles do not change the tenant isolation.

\subsection{Research Challenges}
Previous research has investigated single schema mapping \cite{aulbach2008}, automated query modification \cite{stonebraker1974} and administrative complexity in multi tenant systems \cite{bezemer2010, kabbedijk2015}. However, little research has been performed to investigate the interactions between application (ORM) and database (row level) security when running under high concurrency conditions.

Careful consideration must be given to connection pooling when many tenant changes occur. If physical connections are reused between different requests, session information must be cleared in a reliable manner to ensure tenant information is not passed between users. Furthermore, it is important to understand the performance implications of security policies in modern relational databases. In this paper, these questions are answered by investigating NexusOps in Postgres 17.

\subsection{Adversary and Trusted Computing Base}
An adversary ($\mathcal{A}$) aims to either view, modify or delete data belonging to a different tenant. The adversary is assumed to be a legitimate user in tenant $T_A$. They may attempt to make requests to view data from tenant $T_B$ ($T_A \neq T_B$).

The adversary may perform attacks in a number of ways:
\begin{enumerate}
\item \textbf{API Manipulation:} Manipulating queries sent to the API, such as changing the URL path, guessing sequential IDs (IDOR), or modifying headers (\texttt{X-Tenant-ID}).
\item \textbf{Application Implementation Errors:} Exploiting errors made in the application to gain access to data not intended. For example, if tenant filtering is not applied in ORM, or in native SQL queries, or in repository methods.
\item \textbf{Session Data Leakage:} Leveraging data remaining in pooled database connections. If a connection was used by a request from tenant $T_B$, and re-used for a request from tenant $T_A$, without appropriate sanitisation, data may be leaked.
\end{enumerate}

The Trusted Computing Base consists of the Postgres database, host OS kernel, query compilation perimeter, and RS256 asymmetric signing key.

The two layer isolation technique should prevent data leakage between tenants due to errors in tenant identification, or missing tenant conditions in application. However, both layers rely on the same source of tenant information from the database session: \texttt{app.tenant\_id}.

If an adversary performs stacked SQL injection, they may attempt to run the command \texttt{set\_config('app.tenant\_id', ...)} directly.

As a result, even with RLS enabled it is still important to securely handle user inputs and construct secure queries. Parameterised query compilation and extended query mode have been employed in NexusOps to minimise this risk.

\subsection{Operational Semantics}
To understand how queries are processed within the double isolation model, operational semantics have been defined.

Let $\mathcal{T}$ be the set of registered tenants: $\{t_1, t_2, \dots, t_n\}$. If no tenant context is present (empty), this shall be denoted $\emptyset$.

The state of the database ($\sigma$) contains the set of rows for each relation in the database. Each row will contain a constant tenant ID: $r.\texttt{tenant\_id} \in \mathcal{T}$.

The state of a physical database connection ($C$) contains the ID of the connection ($\mathit{id}$), tenant context ($\tau \in \mathcal{T} \cup \{\emptyset\}$) and whether the connection is in auto commit/transaction mode ($m \in \{\mathit{auto}, \mathit{tx}\}$).

If a query ($\mathcal{Q}$) is issued, a result ($\mathcal{R}$) is returned, and a new database state may be formed. This can be represented as:
\begin{equation}
\langle \mathcal{Q}, \sigma, \tau \rangle \to \langle \mathcal{R}, \sigma' \rangle
\end{equation}

With double isolation, during processing of queries in this system, a tenant filtering operation is applied to the data ($\Pi_\tau$). Only rows with a matching tenant ID will be returned:
\begin{equation}
\Pi_\tau(\sigma(T)) = \{ r \in \sigma(T) \mid r.\texttt{tenant\_id} = \tau \land \tau \neq \emptyset \}
\end{equation}

If a read query ($\mathcal{Q}_{\mathit{read}}(T, \phi)$) is issued with a valid authentication, and $\phi$ is the query criteria from the application, the returned results will be:
\begin{equation}
\mathcal{R} = \{ r \in \Pi_\tau(\sigma(T)) \mid \phi(r) \}
\end{equation}
This can be represented operationally as:
\begin{equation}
\frac{\tau \in \mathcal{T} \quad \mathcal{R} = \{ r \in \Pi_\tau(\sigma(T)) \mid \phi(r) \}}{\langle \mathcal{Q}_{\mathit{read}}(T, \phi), \sigma, \tau \rangle \to \langle \mathcal{R}, \sigma \rangle}
\end{equation}

If a read query is issued without a valid tenant context, an empty result set is returned:
\begin{equation}
\frac{\tau = \emptyset}{\langle \mathcal{Q}_{\mathit{read}}(T, \phi), \sigma, \emptyset \rangle \to \langle \emptyset, \sigma \rangle}
\end{equation}

Write queries function similarly. If a write query ($\mathcal{Q}_{\mathit{write}}(T, r)$) is issued, and the tenant ID in the record does not match the current tenant ($\tau$), then it cannot be inserted. If it does match, then the database state will be updated as $\sigma' = \sigma[T \mapsto \sigma(T) \cup \{r\}]$:
\begin{equation}
\frac{\tau \in \mathcal{T} \quad r.\texttt{tenant\_id} = \tau \quad \sigma' = \sigma[T \mapsto \sigma(T) \cup \{r\}]}{\langle \mathcal{Q}_{\mathit{write}}(T, r), \sigma, \tau \rangle \to \langle \{r\}, \sigma' \rangle}
\end{equation}

If the record belongs to a different tenant, then the query will be rejected by PostgreSQL:
\begin{equation}
\frac{\tau \in \mathcal{T} \quad r.\texttt{tenant\_id} \neq \tau}{\langle \mathcal{Q}_{\mathit{write}}(T, r), \sigma, \tau \rangle \to \langle \text{error}(42501), \sigma \rangle}
\end{equation}
Where error code \texttt{42501} indicates insufficient privilege.

\subsection{Security Properties}
This architecture should provide 5 security properties. These properties have been formally defined.

\noindent \textbf{Property 1 Strict Isolation Between Tenants:} For any query ($\mathcal{Q}$) issued, and any two tenants $t_A$ and $t_B$ in $\mathcal{T}$ ($t_A \neq t_B$), if a query is issued with context $t_A$, then in the results, no rows will have tenant ID $t_B$:
\begin{equation}
\forall r \in \mathcal{R}: \quad r.\texttt{tenant\_id} \neq t_B
\end{equation}
Queries made with context $t_A$ will not return data from tenant $t_B$ \cite{goguen1982}.

\noindent \textbf{Property 2 Fail Safe:} If the session context is empty ($\tau = \emptyset$), the filtering operation returns an empty set:
\begin{equation}
\Pi_\emptyset(\sigma(T)) = \emptyset
\end{equation}
Unless a query is made with a valid authenticated context, no tenant data will be visible.

\noindent \textbf{Property 3 Connection Sanitisation:} At the end of a transaction, when physical connection $C_i$ is returned to the pool, the tenant context associated with it will be removed:
\begin{equation}
\tau(C_i) \to \emptyset
\end{equation}
If a new transaction begins using connection $C_i$, the initial context of the connection will be empty ($\tau = \emptyset$) until it is explicitly bound to a new context.

\noindent \textbf{Property 4 Read-only Audit Logs:} Every event will cause an audit log ($a$) to be added to $\sigma(\mathit{Audit})$. An append only policy is enforced:
\begin{equation}
\forall \sigma \to \sigma', \quad \sigma(\mathit{Audit}) \subseteq \sigma'(\mathit{Audit})
\end{equation}
No audit logs can be modified/deleted using roles in the application.

\noindent \textbf{Property 5 Consistent Response to Enumeration:} If a user from tenant $t_A$ attempts to access an entity with ID $e_{\mathit{id}}$ from tenant $t_B$, the application will respond with:
\begin{equation}
\text{Response}(e_{\mathit{id}}) = \text{HTTP 404 Not Found}
\end{equation}
If an entity does not exist in another tenant, or at all, the application will return the same response. This prevents enumeration attacks through IDOR.

\subsection{Proof By Induction of Isolation in Reused Connections}
An inductive proof is provided to show that isolation is maintained when a query is executed on a reused physical database connection.

Consider $m$ transactions executed in sequence over the same physical connection.

\noindent \textbf{Theorem 1.} Given a sequence of $m$ transactions $\langle tx_1, tx_2, \dots, tx_m \rangle$ run over physical connection $C$, and $tx_i$ is executed on behalf of tenant $\tau_i \in \mathcal{T}$, for all transactions $tx_k$ ($1 \le k \le m$), a record belonging to another tenant $\tau_j$ ($\tau_j \neq \tau_k$) cannot be observed by $tx_k$.

\noindent \textit{Proof by Induction.}

\textbf{Base case ($m = 1$):} Transaction $tx_1$ is executed on connection $C$ with $\tau = \emptyset$. AutoCommit is set to false, and the following is executed:
\begin{lstlisting}[language=SQL]
SELECT set_config('app.tenant_id', t1, true);
\end{lstlisting}
As \texttt{is\_local} is true, this configuration is applied only within $tx_1$. RLS is applied, and rows in relation $T$ will be filtered by $\tau_1$, to give:
\begin{equation}
\{r \in \sigma(T) : r.\texttt{tenant\_id} = \tau_1\}
\end{equation}
Thus, any rows with $r.\texttt{tenant\_id} \neq \tau_1$ will be rejected. Once $tx_1$ has been committed (or rolled back), all session specific configurations within $tx_1$ are cleared. The connection will again have $\tau = \emptyset$. Hence non-interference holds for $m = 1$.

\textbf{Inductive Hypothesis:} Suppose Theorem 1 is true for sequences of length $k$ ($m = k$). This means that for any transaction $tx_i$ ($1 \le i \le k$), no records belonging to other tenants can be observed. Additionally, once $tx_k$ has completed, the session will have $\tau(C) = \emptyset$.

\textbf{Inductive Step ($m = k + 1$):} Transaction $tx_{k+1}$ is executed on connection $C$. Due to the Inductive Hypothesis, connection $C$ has $\tau(C) = \emptyset$ from $tx_k$. If no context is set during $tx_{k+1}$, then property 2 means that $\Pi_\emptyset (\sigma(T)) = \emptyset$, meaning no rows will be returned. If context $\tau_{k+1}$ is set, the following command is run by the interceptor:
\begin{lstlisting}[language=SQL]
SELECT set_config('app.tenant_id', tk+1, true);
\end{lstlisting}
RLS is applied, so only rows belonging to tenant $\tau_{k+1}$ can be seen. For any rows $r$ belonging to tenant $\tau_j$ ($j \le k$), since $\tau_j \neq \tau_{k+1}$, the predicate is false. Once $tx_{k+1}$ completes, the configuration is removed at the transaction boundary. $\tau(C)$ is again $\emptyset$. As this is true for $m = k+1$, Theorem 1 is proved using mathematical induction for all $m \ge 1$. $\blacksquare$

\subsection{Attack Vectors \& Mitigations}
Even if access to rows in a shared schema is restricted, an attacker may still be able to extract information via side-channels. NexusOps mitigates these attack vectors:

\textbf{Unique Constraints.} If a column has a global uniqueness constraint, such as email, an attacker in tenant $T_A$ may be able to determine if an email exists in tenant $T_B$ by attempting to insert a duplicate and causing a unique constraint violation. NexusOps ensures that all uniqueness constraints are scoped by tenant. Thus, uniqueness constraints are:
\begin{lstlisting}[language=SQL]
UNIQUE (tenant_id, email)
\end{lstlisting}
As duplicate values across different tenants do not conflict, it is no longer possible to infer the existence of entities in other tenants.

\textbf{Cache Bleed.} When caching results of queries, the key should contain the tenant identifier. NexusOps ensures all cache keys are scoped by tenant. Cache keys have the format:
\begin{lstlisting}
tenant:{tenant_id}:{entity}:{id}
\end{lstlisting}
So cache entries cannot be accessed across tenants.

\textbf{Constant Response Times.} Both error responses for missing entities, and invalid cross-tenant entities return a status code 404 with the same response body. Therefore, there is no difference in the time taken to return a response, and information about the existence of entities in other tenants cannot be inferred.

\section{System Architecture}
\label{sec:architecture}

Upon receipt of an HTTP request, the perimeter filter verifies the signature on the token, it then extracts the \texttt{tid} claim and creates an immutable \texttt{TenantContext}. The gateway will ignore tenant information in headers (\texttt{X-Tenant-Slug}), form fields and tenant IDs provided in request bodies, to ensure clients cannot change their effective tenant by simply altering request information.

If no valid authentication credentials are provided in requests, an empty tenant context ($\tau = \emptyset$) is created. For synchronous requests, tenant context is passed along the execution chain. Asynchronous requests and Java virtual threads propagate tenant contexts using custom decorators and \texttt{ScopedValue} bindings to ensure tenant information is not unexpectedly passed between unrelated tasks.

\subsection{Virtual Threads \& Scoped Context}
This service is built as a modular monolith using Spring Boot 4 and Java 25. Relational data is stored in PostgreSQL 17, whilst caching and token revocation data is stored in Redis 7 (Fig. \ref{fig:arch}).

Modern runtimes such as Java allow many concurrent requests to be handled by using virtual threads. This means that many requests can be executed concurrently without requiring an operating system thread per request. However, propagating tenant information in requests handled using virtual threads carries new challenges. Request specific data may be stored in traditional thread local variables meaning that if a request is handled with a virtual thread, there is a risk of tenant information leaking into unrelated tasks.

Choosing to build as a modular monolith rather than microservices was intentional. Using a microservices based design can add complexity due to distributed transaction processes, two phase commit (2PC) and inter-operability between networks and multiple databases \cite{dragoni2017}. Using a single application allows NexusOps to perform ACID transactions between related business processes and keep append only audit logs without the need for distributed coordination \cite{richardson2018, newman2019}.

\subsection{Virtual Thread Execution Model}
Virtual threads can be paused and resumed on different threads. Additionally, asynchronous executors may re-use worker threads to execute unrelated tasks. Using \texttt{ThreadLocal} variables in a traditional thread-per-request model commonly allows information such as the authenticated tenant ID to be stored. This can work well for single requests handled in single OS threads. However, if information is not carefully managed, in multi-component services, tenant information from one request can be visible in another.

By splitting the application into individual Java packages based on functionality, NexusOps provides the following packages: Identity \& Tenancy, Authorisation \& RBAC \cite{sandhu1996}, Directory Services (Users, Organisations, Items), and Core Functional Components (CRM, Pipelines, Invoices, Ledgers). Spring Modulith has been used to enforce module boundaries. Dependencies between packages are checked at build time to enforce the intended structure of the application and identify any violations.

\subsection{Scoped Value Tenant Context}
Java 25 scoped values have been used in combination with a custom \texttt{TenantAwareTaskDecorator} to manage tenant context. All 16 tables representing data owned by tenants have consistent RLS configurations (Fig. \ref{fig:schema_er}). A central security infrastructure provides a tenant context, data source aware of tenants, shared entity definitions, verification of roles within the database and scoped tenant context propagation for all application modules. Within this scoped value, all domain table data owned by tenants use the same configuration. Once a tenant ID has been determined for a request:
\begin{lstlisting}[language=Java]
ScopedValue.where(TENANT_SCOPE, tenantId)
    .run(() -> executor.execute(task));
\end{lstlisting}
Scoped value is used to provide a bound, immutable context. Within this scope, the current tenant ID cannot be overwritten. When execution exits this scope, the scoped value is automatically unbound. It is not required for developers to manually clean up resources in \texttt{finally} blocks.

This fits well with virtual thread execution. If a virtual thread is blocked during an operation, such as socket I/O, the JVM can unbind it from its carrier thread, before re-binding it to an available thread. Since the scoped value is scoped to the execution of the virtual thread rather than to the carrier thread, the tenant ID is still correctly associated with the logical task. This prevents tenant context leakage.

\subsection{Scope ORM to Tenants (Layer 1)}
All entities within the domain model of NexusOps extend a single base class containing a tenant identifier:
\begin{lstlisting}[language=Java]
@MappedSuperclass
public abstract class TenantEntity {
  @TenantId
  @Column(name = "tenant_id", nullable = false, updatable = false)
  private UUID tenantId;
}
\end{lstlisting}
\textbf{Current Tenant Deletion Resolution:} When multi-tenancy is configured in the application, the \texttt{CurrentTenantIdentifierResolver} is registered to return the current active tenant identifier \cite{hibernate2025}. When generating queries in JPA, Hibernate appends: \texttt{AND tenant\_id = :currentTenant} to the SQL. Any inaccessible records will return a 404 error.

\textbf{Limitations of ORM Filtering:} Queries written as native SQL, JDBC operations, bulk updates, or analytical queries may execute without being filtered by Hibernate. For example, if a developer forgets to include a tenant filter in a native SQL query, they may accidentally expose/modify data from other tenants. As a result, multi-tenancy cannot be solely enforced at the ORM. It must also be enforced at the database.

\subsection{Enforce RLS (Layer 2)}
To scope any queries outside of the ORM, RLS is enabled and enforced for all tenant-owned tables:
\begin{lstlisting}[language=SQL]
ALTER TABLE <tbl> ENABLE ROW LEVEL SECURITY;
ALTER TABLE <tbl> FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON <tbl> FOR ALL TO nexusops_app
  USING (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid);
\end{lstlisting}
This policy enforces tenant scoping in both read and write operations. Rows in the table that match the \texttt{USING} clause will be returned in response to read operations. Only rows that match the \texttt{WITH CHECK} clause will be inserted or updated using write operations.

\textbf{Database Roles and Privileges:} Schema migrations are performed during deployment of the application using the \texttt{nexusops\_owner} role. This role has ownership of tables, and includes the required \texttt{BYPASSRLS} attribute to allow creation/alteration of database objects. However, the live application connects with the limited role \texttt{nexusops\_app}. This does not have \texttt{BYPASSRLS}, and therefore can not alter table structures or create new objects within the database \cite{postgresql17docs}. Audit tables are protected using database triggers to prevent unauthorised updates/deletes. \texttt{TRUNCATE} has been denied (Property 4).

\textbf{Dealing with missing/incorrect tenant identifiers:}
The \texttt{current\_setting('app.tenant\_id', true)} function is wrapped within a \texttt{NULLIF} statement. If the tenant identifier is missing, it evaluates to NULL, thus enforcing fail-closed behaviour in accordance with SQL three-value logic. However, if an invalid UUID format is provided, this will raise an error in PostgreSQL (error code \texttt{22P02}) and cause the transaction to fail.

\subsection{Connection Sanitization across Recycled Pools}
Connection pools (HikariCP) can be used by production application servers to efficiently manage connections to databases. Rather than creating a new connection to the database for every request, connections are reused between many transactions. If session settings are run in auto COMMIT mode, then on check out the settings will be reset.

To avoid this, NexusOps delays tenant binding until the database transaction begins. This means that the connection lifecycle follows 5 stages (Fig. \ref{fig:state_machine}):
\begin{enumerate}
\item \textbf{S0 – Pool Idle:} An idle connection exists in the HikariCP connection pool, with no active tenant context ($\tau = \emptyset$).
\item \textbf{S1 – Transaction Commenced:} A connection is taken from the pool by the transaction manager. The connection is set to have \texttt{autoCommit = false}.
\item \textbf{S2 – Tenant Context Bound:} Once the first query is made by a repository, \texttt{app.tenant\_id} is set in the current transaction.
\item \textbf{S3 – DML Bound:} Queries run in the application, with both Hibernate and RLS filtering applied.
\item \textbf{S4 – Clean-Up:} Once the transaction has completed with either \texttt{COMMIT} or \texttt{ROLLBACK}, the in-transaction setting is removed and the connection is returned to the pool.
\end{enumerate}

\begin{lstlisting}[language=Java,caption={Transaction Connection Interceptor}]
public class TenantConnectionInterceptor implements ConnectionProvider {
  @Override
  public Connection getConnection() throws SQLException {
    Connection connection = dataSource.getConnection();
    if (!TransactionSynchronizationManager.isActualTransactionActive()) {
      return connection;
    }
    String currentTenant = TenantContextHolder.getTenantId();
    if (currentTenant != null) {
      try (PreparedStatement stmt = connection.prepareStatement(
          "SELECT set_config('app.tenant_id', ?, true)")) {
        stmt.setString(1, currentTenant);
        stmt.execute();
      }
    }
    return connection;
  }
}
\end{lstlisting}
A connection is obtained from the data source. If there is an active Spring transaction and a tenant ID, then the tenant ID is set in the current transaction. If there is no transaction, then the connection is simply returned.

\section{Automated Guardrails}
\label{sec:guardrails}

Within a rapidly changing development environment, just enforcing security controls via code review and developer awareness is insufficient. If a new table is created in a migration without enabling RLS, a vulnerability may be introduced without an apparent error in the application.

To mitigate this risk, NexusOps includes 3 automation safeguards in development and deployment: Build-time catalog verification, policy mutation testing, and runtime database role verification.

\subsection{Build-time Catalog Verification and AST Verification}
\texttt{RlsCoverageIT} is included in NexusOps' integration tests. This runs during Maven builds. It sets up a temporary PostgreSQL instance using Testcontainers. The latest migrations are run, and security configurations are checked within \texttt{pg\_class}, \texttt{pg\_namespace}, \texttt{pg\_policy}, and \texttt{pg\_views}:
\begin{lstlisting}[language=SQL]
SELECT c.relname, p.polname
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
LEFT JOIN pg_policy p ON p.polrelid = c.oid
WHERE n.nspname = 'public'
  AND c.relkind IN ('r', 'p')
  AND c.relname NOT IN ('permissions', 'subscription_plans')
  AND (NOT c.relrowsecurity OR NOT c.relforcerowsecurity OR
       p.polname IS NULL OR p.polcmd <> '*' OR NOT p.polpermissive OR
       (pg_get_expr(p.polqual, p.polrelid) IS DISTINCT FROM :canonicalExpr) OR
       (pg_get_expr(p.polwithcheck, p.polrelid) IS DISTINCT FROM :canonicalExpr) OR
       (SELECT count(*) FROM pg_policy WHERE polrelid = c.oid) != 1);
\end{lstlisting}
The canonical tenant isolation expression is given as:
\begin{lstlisting}[language=SQL]
tenant_id = (NULLIF(current_setting('app.tenant_id'::text, true), ''::text)::uuid)
\end{lstlisting}
The PostgreSQL function \texttt{pg\_get\_expr()} allows us to extract more legible SQL expressions from the saved expression trees. These extracted expressions can be compared to the canonical expression by NexusOps.

Policy anomalies:
\begin{itemize}
\item \textbf{RLS and FORCE RLS should be enabled.} Within every tenant table, both \texttt{relrowsecurity} and \texttt{relforcerowsecurity} should be enabled. When FORCE RLS is not enabled, then restrictions for the row-level security may be breached by the table owner.
\item \textbf{The policy should be correctly configured.} Both \texttt{polqual} and \texttt{polwithcheck} should match the expected tenant restriction.
\item \textbf{Only one permissive policy allowed per relation.} Having more than one permissive policy may unintentionally allow wider access in PostgreSQL, given that policies combine using OR logic.
\item \textbf{Views must be secure invoker.} If a view accesses tenant data in the database, the view must have \texttt{security\_invoker = true} so that access is restricted according to the permissions and RLS context of the user initiating the request.
\end{itemize}
If any of these conditions are not met, the relation is highlighted by the catalog check and build fails.

\subsection{Mutant Policies within 4 Quadrants}
While catalog checks can detect missing or incorrect policies, we must test that they do so effectively. NexusOps provides a testing script (\texttt{verify\_policy\_guard.sh}) that creates 16 erroneous variants of the schema, known as mutants.

Mutants fall under 4 quadrants.

\textbf{Quadrant 1: Missing flags and accidental privilege holes.} Mutants 1 (No RLS), 2 (Owner Privilege By-pass), 5 (Missing Write Check) and 8 (Privilege leak in maintenance roles) create errors in policy configuration. Mutant 1 does not enable RLS. Mutant 2 enables RLS, but not FORCE RLS allowing the table owner to bypass restrictions. Mutant 5 does not include a WITH CHECK clause. Mutant 8 simulates maintenance operations (i.e. administration) on tables that do not have FORCE RLS enabled. All 4 mutants were identified by catalog checks.

\textbf{Quadrant 2: Incorrect predicates and permissive policies.} Mutants 3 (Write permission hole), 4 (Read permission hole), 7 (Incorrect column filtering), 8b (Missing NULLIF), 13 \& 14 (Tautology injection using OR TRUE), 15 (Hard-coded UUID constant) and 16 (Incorrect variable name used for session variable-GUC drift) create incorrect policies. Mutant 3 contains \texttt{WITH CHECK (true)} meaning there is no restriction on writing. Mutant 4 contains a \texttt{USING (true)} clause, therefore any row is visible. Mutant 7 filters based on \texttt{created\_by} and not \texttt{tenant\_id}. Mutant 8b removes \texttt{NULLIF}, which could cause exceptions when initial values have not been set. Mutants 13 \& 14 inject tautological conditions using OR TRUE. Mutant 15 hard-codes a UUID value. Mutant 16 uses an incorrect variable name corresponding to the session variable. All 7 mutants differ from the canonical expression in policy, and so were identified by AST comparisons.

\textbf{Quadrant 3: Role misconfiguration and Restrictive Deadlocks.} Mutants 6 (Permissive policies with OR logic), 9 (Orphan restrictive policy), 11 (Policies applied to only some commands) and 12 (Policies applied to only some commands) produce incorrect policies. Mutant 6 adds a second permissive policy allowing wider access due to OR logic. Mutant 9 adds a restrictive policy with no corresponding permissive policy causing a service denial. Mutants 11 and 12 add policies to only a subset of commands (SELECT/INSERT) and not all commands (\texttt{*}). All 4 mutants were identified by audit checks.

\textbf{Quadrant 4: Insecure views.} Mutant 10 (Incorrectly configured view) creates an analytic view over tenant data, however does not include \texttt{security\_invoker = true}. By default, permissions on this view are applied according to the creator, therefore RLS is ineffective. This is flagged by NexusOps in \texttt{pg\_views}.

All 16 mutants were blocked by guardrails, achieving 100\% detection rate.

\subsection{Role Checks During Start-up}
Even if a secure design seems apparent, it is important to understand whether a system is secure in practice. In particular, developers may make mistakes during development. They may forget to add annotations, perform unsafe database queries, or run migrations with incomplete security policies. Even if a defence-in-depth design is implemented, vulnerabilities may exist within the system.

We simulated 16 scenarios of failure in application, database, connection handling and infrastructure, shown in Table \ref{tab:fault_injection}.

If a superuser account, or account with the \texttt{BYPASSRLS} attribute, is used during runtime, then policies that restrict row access may be bypassed.

Multiple scenarios demonstrate the need to provide isolation at multiple layers. Omitting \texttt{@TenantId} from a new JPA entity (Scenario 1) or running a native SQL query without a tenant predicate (Scenario 2) will allow bypassing of the application ORM filtering. However, row level security is still in place in PostgreSQL and will therefore return only rows belonging to the tenant in the current transaction.

Similarly, re-using a connection from a different tenant may mean that incorrect filtering applies if connection state is not correctly reset. Scenario 4 demonstrates this. While the database protects against accessing rows from the previous tenant, an automated test ensures that connections behave as expected.

\subsection{Concurrency Benchmark and Positive Controls}
Whilst unit testing can help to detect issues, concurrency related issues may be harder to detect. In a multi-tenanted system, connection reuse, async delegation and quickly changing tenant contexts can cause short lived data inconsistency issues. These concerns are especially important to consider if the number of requests is large and the number of database connections available is limited.

To test for these cases in NexusOps, 1,000,000 requests were made across tenants. These were made by 100 concurrent threads. These threads used a HikariCP connection pool providing 32 connections to the database. In total, 940,000 tenant context switches occurred across 100 organisations and 16 business tables.

\textbf{Canary Token Check:} Each persisted data record contains an encrypted canary token:
\begin{lstlisting}
canary_{tenant_id}_{uuid}
\end{lstlisting}
During the test, each client checked whether the tenant identifier contained in every returned record's canary token matched the tenant associated with its JWT claim. If a record belonging to another tenant appeared in a response, the harness stopped the test immediately.

\textbf{Positive Controls and Verification:} If we are to trust that a failure has been detected by a test harness, then we must be able to confirm that the harness can indeed detect failures. As such we ran 3 positive control tests:
\begin{enumerate}
\item \textbf{Filter Only (ORM Layer):} In this configuration, the database tables were shared, and no row level security was configured at the database level. Out of 10,000 probe requests, all cross-tenant requests were blocked by the row level security policy.
\item \textbf{Cleaned Filtering (Protocol Layer):} In this configuration, tenant filtering was implemented within the application (as in 1), but in addition, when a connection was checked out, the tenant session variable was assigned. At the database layer, row level security was disabled. Zero leaks were observed in this configuration.
\item \textbf{Both Protection Layers (Forced RLS + Filters):} In this configuration, filtering was implemented at both the ORM and database layers. The tenant context was assigned in the database session, and the relevant security predicates were checked by PostgreSQL when the same queries were run as in 1) and 2).
\end{enumerate}
From this we can see that the test harness could differentiate between configurations where protections were applied, and those where protection was intentionally turned off.

\textbf{Rule of Three Confidence Interval:} Throughout this concurrency test, there were no cross tenant record leaks in any of 1,000,000 requests.

Whilst the absence of leaks suggests that a cross tenant leak has zero probability, we must instead find an upper confidence interval that this is the case. Using Hanley--Lippman-Hand's Rule of Three \cite{hanley1983}, for $N$ independent observations with no events, we can find an approximate upper 95\% confidence interval:
\begin{equation}
p_{95\%} < \frac{3}{N}
\end{equation}
With our observed number of requests:
\begin{equation}
p_{95\%} < \frac{3}{1,000,000} = 3 \times 10^{-6} \quad (0.0003\%)
\end{equation}
This means that we can have approximately 95\% confidence that the probability of a cross-tenant data leak occurring in this test is less than 0.0003\%.

Therefore, we have empirical evidence that reset between transactions, connection clean-up and tenant context propagation have worked correctly within this workload. However, this should be considered within the constraints of this test. We cannot be universally assured that queries not tested will not cause issues, or that tenant credentials will not be compromised, or vulnerabilities in lower layers of the database do not exist.

\section{Performance Evaluation}
\label{sec:evaluation}

\subsection{Methodology}
In order to evaluate the performance of this defence in depth architecture, two types of overheads should be considered. The first is the overhead from having to assign the tenant session variable in addition to the query. The second is the overhead of checking row level security predicates in PostgreSQL. If we measured both of these overheads, it would be difficult to determine how much overhead each security mechanism is contributing.

Therefore, we ran this benchmark in PostgreSQL 17.11, to compare 3 configurations in controlled conditions:
\begin{enumerate}
\item \textbf{Filter Only (ORM Layer):} In this configuration, the database tables were shared, and no row level security was configured at the database level. However, tenant filtering was implemented within the application with queries containing conditions such as \texttt{WHERE tenant\_id = ?}. No \texttt{set\_config()} call was required.
\item \textbf{Cleaned Filtering (Protocol Layer):} In this configuration, tenant filtering was implemented within the application (as in 1), but in addition, when a connection was checked out, the tenant session variable was assigned. At the database layer, row level security was disabled. Zero leaks were observed in this configuration. Therefore, we can measure how much extra communication between client and server is required in order to set up the tenant context.
\item \textbf{Both Protection Layers (Forced RLS + Filters):} In this configuration, filtering was implemented at both the ORM and database layers. The tenant context was assigned in the database session, and the relevant security predicates were checked by PostgreSQL when the same queries were run as in 1) and 2).
\end{enumerate}

The benchmarks evaluated Point Lookups (Single Record Queries), Paged Lists (20 Sorted Records), Tenant Count Aggregation and Point Inserts with RLS \texttt{WITH CHECK} condition policies. This dataset consists of 1,000,000 records spread equally across 100 organisations (10,000 records per organisation). Each record has a 64-bit Integer Primary Key, 128-bit UUID Tenant ID and standard business data. The table includes a compound index on \texttt{(tenant\_id, name)}.

All experiments were conducted on a dedicated Linux machine running PostgreSQL 17.11 (kernel version: 6.6, 10 vCPUS, 16GB RAM, NVMe SSD). The configuration had \texttt{shared\_buffers=4GB}, \texttt{work\_mem=64MB}, \texttt{max\_connections=200} and \texttt{synchronous\_commit=off}. 8 clients were used in parallel with 4 worker threads for 2 seconds (after any unmeasured warmup time). The tables were emptied, re-populated and vacuumed between each test cycle. As standard in benchmarking studies \cite{georges2007, kalibera2013, mytkowicz2009}, $n=30$ randomized pairs of tests were conducted for each workload.

\subsection{Throughput, Latency and Statistical Equivalence}
\textbf{Comparison to Baseline (Filter Only):} Using the baseline workload as a reference, Dual-Layer has a throughput ratio of between $0.726$ and $0.907$, dependent on microbenchmark.

It should be noted that this comparison accounts for overhead from both configuration and RLS. To determine the overhead from just the database, Dual-Layer RLS and Filter + Sanitized configurations were compared. In this case, the configuration overhead is identical. The difference in performance therefore predominantly reflects the extra computation in PostgreSQL RLS. The least overhead occurred in point inserts (throughput ratio: $0.977$, 95\% CI: $[0.947, 1.007]$), equivalent to an overhead of approximately $2.3\%$. Read workloads had an overhead of approximately $6.3$--$8.8\%$ compared to the baseline.

\textbf{Separation of Protocol and Database Overhead:} There are two main reasons for the observed performance difference. Firstly, the \texttt{set\_config()} function requires an additional round trip which adds $0.17$--$0.44$ ms to the transaction in short (single statement) queries.

Tables of throughput and latency for the 30 paired runs are shown in Table \ref{tab:benchmarks}. Transaction latency was calculated as the inverse of the transaction rate ($L = c/\text{tps}$). However, 99th percentile tail latency was directly extracted from transaction logs (\texttt{-l} option in pgbench). Mean and Tail latency results are shown in Figure \ref{fig:latency_comp}.

\textbf{Statistical Equivalence (TOST):} While statistical differences may exist between configurations, they may not be operationally meaningful. The Two One-Sided Test (TOST) \cite{schuirmann1987, lakens2018} was therefore used to determine whether Dual-Layer RLS was within a pre-defined range of statistical equivalence to the baseline ($\pm 10\%$, $\theta_L=0.90$, $\theta_U=1.10$). Logarithmic transformation was applied to throughput ratios:
\begin{equation}
z_i = \ln\left(\frac{\text{Throughput}_{\text{Dual},i}}{\text{Throughput}_{\text{Sanitized},i}}\right)
\end{equation}
Results from TOST suggest that there was a statistically meaningful difference between Dual-Layer RLS and the baseline in Paged List ($p=2.33 \times 10^{-3}$), Tenant Count ($p=3.22 \times 10^{-2}$) and Point Insert ($p=5.55 \times 10^{-6}$). However, in Point Insert workloads, $d=-0.98$ and the CI $[0.947, 1.007]$ crosses 1.0. This means that the throughput in point inserts was effectively equivalent to the baseline (within $2.3\%$ overhead). Figure \ref{fig:ratio} shows paired throughput ratio results compared to baseline, including a corridor representing $\pm 5\%$ statistical equivalence.

\subsection{Complex Workloads}
Workloads in practice can be complex. Relational joins often occur, organisations can have very different data volumes, and high connection demand may be experienced. Therefore, relational joins, skewed tenant volumes and connection pool saturation were investigated (Table \ref{tab:complex_benchmarks}, $n=30$ paired runs).

\textbf{Throughput and Latency in Relational Graph Joins and Foreign Key Filtering:} In 2 table joins (\texttt{orders} $\bowtie$ \texttt{order\_items}), throughput ratio was $0.731$ (95\% CI: $0.712$--$0.750$), and in 3 table joins ($\bowtie$ \texttt{order\_payments}) throughput ratio was $0.736$ (95\% CI: $0.720$--$0.752$). The throughput ratio in these workloads was consistent for increasing join depth, as long as composite indexes and tenant qualified relationships existed. As client count was increased from 8 to 32, against a 32 connection HikariCP pool (see Figure \ref{fig:concurrency_scaling}), mean transaction latency was $1.05$ ms (baseline) and $1.40$ ms (Dual-Layer RLS). When increasing to 32 clients (pool saturation), latency increased to $3.54$ ms (baseline) and $4.94$ ms (Dual-Layer RLS). p99 tail latency was $9.59$ ms and $12.50$ ms respectively. During saturation, contention in the connection pool and queuing on the network became the main source of latency. This dominated the sub-ms latency overhead from evaluating RLS conditions. Including the entire HTTP stack (Spring Boot, HikariCP, JSON serialization), mean request latency was $2.4$ ms and p99 was $6.8$ ms.

\textbf{Skewed Tenants and General Cache Planning:} In real world SaaS applications, it is common for tenant records to be unevenly distributed. Here, we consider an 80/20 distribution. The dataset consisted of 250,000 records in a large tenant (25\%) and 500 records in smaller tenants (0.05\%) (100 organisations in total). Small tenants had a throughput ratio of $0.719$ (95\% CI: $0.703$--$0.734$) ($9,296$ tps). The large tenant (whale tenant) had a throughput ratio of $0.713$ (95\% CI: $0.701$--$0.725$) ($9,568$ tps). Composite indexes ensure \texttt{tenant\_id} is the leading column so B-trees have 3 levels for all tenant sizes. All tenants had a hit rate in shared buffers $> 99.8\%$. After 5 runs, PostgreSQL switched from using bespoke plans to general cached plans. Session variables are evaluated during scan initialization. Leading index key probing occurs.

\subsection{Memory Usage and Resource Utilization}
Only minor increases in memory usage were observed. Memory usage per connection increased from $8.4$ MB (Filter Only Baseline) to $8.6$ MB (Dual Layer RLS). Hit rates in shared buffers were similar ($99.88\%$ vs $99.85\%$). However, user CPU utilization increased from $54.8\%$ (Sanitized) to $58.1\%$ (Dual-Layer). System CPU increased from $10.1\%$ to $10.8\%$. WAL write speed increased slightly ($12.5$ MB/s to $12.8$ MB/s). Context switches increased from 18,400 per second to 19,100 per second. These results indicate that the RLS implementation caused a relatively small increase in CPU usage ($3.3\%$), however memory usage and hit rates in buffers were effectively identical (Table \ref{tab:resources}).

By observing PostgreSQL execution plans using \texttt{EXPLAIN (ANALYZE, BUFFERS, VERBOSE)}, it can be seen that for the given aggregation queries, the Filter-Only Baseline and Dual-Layer approaches both result in similar execution plans. \section{Developer Experience}
\label{sec:developer_experience}

Implementations of security controls adding significant complexity to operations may have poor compliance. We evaluate the developer experience, database schema migration, and troubleshooting processes in NexusOps to determine whether dual-layer tenant isolation is viable.

\subsection{Developer Experience}
With application-level filtering, developers must manually verify tenant parameters have been correctly applied in every query. With dual-layer tenant isolation, the tenant isolation becomes default functionality.

Standard business logic can be expressed by extending the \texttt{TenantEntity}. The \texttt{@TenantId} is automatically resolved by Hibernate due to a registered context resolver. Spring Data repositories can be written in a standard format, without manually adding tenant parameters to queries.

Queries which bypass the ORM are still protected by RLS. This includes queries created via \texttt{createNativeQuery()} or native queries in Spring Data using \texttt{@Query(nativeQuery = true)} without a tenant discriminant. In an application-level filtering system, this could result in data being returned from other tenants. However, in NexusOps, RLS is forcibly added to the query to restrict results to current tenant. As RLS is forcibly applied, RLS ensures that only data from the current tenant are returned.

This can also be applied during database development. If during a Flyway migration, a new table is created but RLS is not enabled, or forcibly applied, then the \texttt{RlsCoverageIT} integration test in the database catalog will fail. This test is run as part of the local CI process. If this test fails, the build will be failed in just 4.2 seconds on a local laptop. \subsection{Zero Downtime Schema Migration}
Database schema changes are critical in SaaS applications as they must be highly available. When new tables are added for tenants, Flyway migrations are coupled with automated checks to ensure RLS policies are in place. To add a new tenant facing table, the migration performs the following steps:
\begin{enumerate}
\item Create a new table with \texttt{(tenant\_id, id)} as the composite primary key.
\item Enable RLS on the table (\texttt{ALTER TABLE ... ENABLE ROW LEVEL SECURITY}).
\item Enforce RLS (\texttt{FORCE ROW LEVEL SECURITY}).
\item Add canonical tenant policy.
\end{enumerate}
As part of the CI/CD pipeline, when moving to staging, a clean PostgreSQL instance is created via Testcontainers. \texttt{RlsCoverageIT} is run, and if there are missing RLS policies, the build will automatically fail.

\subsection{Isolated troubleshooting}
Troubleshooting consoles connect to their own connection pool (\texttt{PlatformAdminDataSource}) with restricted access with the role \texttt{nexusops\_platform}. Troubleshoot engineers gain temporary (5 minute) access tokens, requiring two person authentication, tied to an open ticket for a specific customer. All queries made log a read-only entry in \texttt{audit\_events}, capturing information about who performed the query, which organisation they were querying, the ticket reference, and the SHA256 hash of the SQL queried.

\section{Discussion}
\label{sec:threats}

\textbf{Internal Validity:} The performance tests were conducted on dedicated hardware, CPU were fixed in place, and memory had no overlap between tests. To reduce variance caused by JIT compilation and caching in JVM, the test order was randomised and warm up phases were excluded \cite{georges2007}. To avoid dead tuple bloat impacting results, tables were truncated, seeded and vacuumed between write operations.

\textbf{External Validity:} In real world SaaS applications, complex joins exist between customers. Additionally, customer data distributions may be heavily skewed. Here, we have tested queries with joins between up to 3 relations and 80/20 distributions (Table \ref{tab:complex_benchmarks}). If complex recursive queries or predicates on unindexed fields are used, the optimiser may produce different execution plans. However, in enterprise environments where composite indexing is common, execution plans for index scans should be consistent across join hierarchies.

\textbf{Construct Validity / Attack Surface:} ORM and native queries that miss tenant filters are caught by RLS. IDOR attacks are blocked at both layers. Connection leaks are prevented through transaction hooks. However, arbitrary SQL injections with application level permissions are not prevented by RLS. An attacker could directly call \texttt{set\_config()}, therefore parameterised queries and prepared statements are essential.

\textbf{Policy Complexity:} Here we have tested simple equality conditions on indexed fields. If subqueries or non secure functions are included in policies, it may prevent index pushing and increase CPU usage per row. Policies for tenants should be simple and align with indexes.

\section{Limitations and Future Work}
\label{sec:limitations}
Despite the strong tenant isolation achieved with minimal overhead, there are limitations to consider.

Using external connection pooling tools (PgBouncer/Odyssey), multiple clients share connections. With \texttt{is\_local = true}, connections behave as expected in connection pooling modes. However, we did not directly test intermediate multiplexing in this physical environment. Similarly, with vector similarity searches (pgvector), there are implications. If RLS filters are applied to HNSW graphs, performance may be reduced if filtering occurs after traversal of the graph. Partitioning vectors per tenant may produce a more predictable design. Additionally, JWTs only last 15 minutes. If compromised, they can remain valid for 15 minutes before they need to be invalidated in Redis. Finally, benchmarks were performed in a single node PostgreSQL setup. In distributed DBMSs (Citus/CockroachDB/Spanner), distributed consensus will add overhead, which we would need to evaluate separately.

Further work will be done into deploying in multi region environments and using cryptographic signed session tokens, validated in the database engine.

\section{Conclusion}
\label{sec:conclusion}
If tenant isolation is left to developer discipline in shared schema SaaS databases, a risk exists. If just one query misses a tenant filter, confidential data can be exposed. To mitigate this, NexusOps uses a dual-layer approach, with application-level ORM filtering and forced RLS in PostgreSQL to provide layered protection. Catalog validation in CI, role verification on start up and sanitising connections in transactions ensure no drift in configuration, contamination of connection pools, or elevation of privileges. We have empirically tested the solution on 1,000,000 records with 30 paired trials. We observe minimal overhead from forcing RLS at the database level ($2.3\%$ to $8.8\%$ higher than sanitised baselines). Two One Sided Tests show statistical equivalence within an operational tolerance of $\pm 10\%$. The platform has low latency when performing complex joins between multiple tables, with skewed tenant distributions, and saturated connection pools. The dual-layer approach moves tenant isolation to kernel-level invariants to provide a robust solution for multi-tenant SaaS applications.
