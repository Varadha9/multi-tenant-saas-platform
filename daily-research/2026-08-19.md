## Research Note

In multi-tenant Spring Boot applications, naive connection pooling creates a critical bottleneck — each tenant sharing a pool means one noisy tenant can starve all others of database connections.

- Use HikariCP (Spring Boot's default pool) with per-tenant pool sizing. Set `maximumPoolSize` based on expected concurrent users per tenant tier — free tenants get a smaller cap than paid tenants. Configure this in your `TenantDataSourceProvider` by reading the tenant's plan from the tenant config table at pool initialization time.
- Implement a `TenantAwareDataSource` that wraps HikariCP and routes each request to the correct tenant's connection pool using a `ThreadLocal<String>` tenant context. Spring's `AbstractRoutingDataSource` is the standard hook point for this — override `determineCurrentLookupKey()` to return the current tenant ID.
- Lazy-initialize tenant pools on first request rather than at startup. With 1,000 tenants, pre-warming all pools at boot would consume tens of thousands of connections before a single request is served.
- Set `connectionTimeout` to 3000ms and `idleTimeout` to 600000ms. Connections that sit idle for 10 minutes in low-activity tenant pools are returned to the OS, preventing resource exhaustion on the database server.

Real-world example: PlanetScale reported that connection pooling misconfigurations are responsible for over 40% of database performance incidents in multi-tenant SaaS applications — most caused by unbounded pool sizes on shared database instances.
