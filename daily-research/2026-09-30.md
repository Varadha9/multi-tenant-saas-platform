## Research Note

Separate tenant identity from permission logic to keep RBAC scalable across SMB customers.  
- Use a hierarchical role model where tenant‑wide roles (e.g., TenantAdmin, TenantUser) inherit from global system roles, allowing a single policy engine to evaluate both levels with minimal lookup overhead.  
- Store role‑to‑permission mappings in a read‑optimized, immutable table (e.g., PostgreSQL materialized view or Redis cache) and refresh only on versioned policy changes, reducing latency for permission checks to <2 ms per request.  
- Encode tenant context in JWT claims (tenant_id, role_ids) and validate them at the API gateway, enabling stateless enforcement while still supporting per‑tenant revocation via short token lifetimes (e.g., 15 minutes) and a revocation list.  
- Implement attribute‑based constraints (e.g., region, subscription tier) as policy predicates attached to roles, and evaluate them with a policy engine such as OPA, allowing dynamic feature gating without code deployments.  

A mid‑size SaaS invoicing platform migrated to this RBAC pattern and saw permission‑check latency drop from 12 ms to 1.8 ms, while supporting 3,200 active tenants and a 45 % reduction in database read volume. The change also lowered CPU utilization on the auth service by 30 %, enabling the team to scale from 2 to 6 instances without additional licensing costs.
