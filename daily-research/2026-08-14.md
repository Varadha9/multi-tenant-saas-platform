# Research: Soft Delete vs Hard Delete in SaaS Databases

## Research Note

Soft delete is the correct default for multi-tenant SaaS — it preserves audit trails, enables recovery, and prevents accidental data loss that tenants cannot undo.

- Soft delete adds an `is_deleted BOOLEAN DEFAULT FALSE` and `deleted_at TIMESTAMP` column to every business data table. Queries filter with `WHERE is_deleted = FALSE` automatically via a Hibernate `@Where` annotation or a Spring Data JPA base repository.
- Hard delete should only be used for compliance-driven erasure requests (e.g., GDPR right to erasure). Build a separate scheduled job that permanently purges soft-deleted records older than 30 days only when a verified deletion request exists.
- Add a partial index on `is_deleted` in PostgreSQL: `CREATE INDEX idx_leads_active ON leads(tenant_id) WHERE is_deleted = FALSE`. This keeps query performance identical to a table without soft delete since the index only covers active rows.
- Expose a "Recently Deleted" UI section per module so tenant admins can restore accidentally deleted records within the retention window — this single feature dramatically reduces support tickets.
- Never soft-delete tenant or user account rows directly. Instead use a separate `status` enum (`ACTIVE`, `SUSPENDED`, `DELETED`) to avoid conflicts with login and billing logic.

Real-world example: Notion uses soft delete across all content. Their "restore from trash" feature is cited in user research as one of the top 3 reasons SMB teams trust the platform with critical data.
