## Research Note

Background jobs in multi-tenant Spring Boot apps must carry tenant context explicitly — the thread running a scheduled job has no HTTP request, so there is no automatic tenant resolution from a JWT.

- Store a `TenantContext` as a `ThreadLocal<String>` utility class. Before any scheduled job executes business logic, set `TenantContext.setTenantId(tenantId)` and clear it in a `finally` block to prevent context leaking across job executions.
- For jobs that run per-tenant (e.g., sending daily digest emails to all active tenants), query the `tenants` table for all active tenant IDs at job startup, then iterate and set context for each tenant before processing their data.
- Use Spring's `@Scheduled(cron = "0 0 8 * * *")` for fixed schedules. For tenant-specific schedules (e.g., a tenant wants reports at 9 AM their timezone), store the cron expression in the `tenant_settings` table and use a `TaskScheduler` bean to register dynamic triggers at runtime.
- Wrap each tenant's job execution in a try-catch so one failing tenant does not abort processing for all others. Log failures with tenant ID for observability.

Real-world example: Freshdesk runs per-tenant SLA breach notification jobs every 15 minutes across 60,000+ tenants using a similar fan-out pattern, processing each tenant's tickets in isolated thread contexts.
