## Research Note

In multi-tenant SaaS, rate limiting must be enforced per tenant — not globally — to prevent one tenant from degrading service for others.

- Implement rate limiting at the API gateway layer (e.g., Spring Cloud Gateway or NGINX) using tenant ID extracted from the JWT, so limits are scoped per workspace before requests even reach business logic.
- Use a token bucket or sliding window algorithm. Token bucket allows short bursts (good for SMB usage patterns), while sliding window gives smoother enforcement. Redis is the standard backing store for distributed rate limit counters.
- Define tiered limits by plan: free tenants get 100 requests/min, paid tenants get 1000/min. Store these limits in the tenant configuration table and load them at middleware startup.
- Always return `429 Too Many Requests` with a `Retry-After` header so clients can back off gracefully instead of hammering the server in a retry loop.
- Return rate limit headers on every response (`X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`) so frontend dashboards can display usage to tenant admins.

Real-world example: Stripe enforces 100 read requests/second per API key. When they introduced per-key rate limiting, support tickets related to cascading failures from noisy tenants dropped by 40%.
