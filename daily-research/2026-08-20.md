## Research Note

Webhooks are the backbone of SaaS integrations — but without proper design, they become a source of data loss, security vulnerabilities, and cascading failures across tenant systems.

- Store every outbound webhook event in a `webhook_events` table with status (`pending`, `delivered`, `failed`) before attempting delivery. This gives you a retry queue and an audit trail. Never fire-and-forget — if the HTTP call fails, the event must be retryable from the stored record.
- Implement exponential backoff for retries: attempt at 0s, 30s, 5min, 30min, 2hr, 24hr. After 24 hours of failures, mark the endpoint as `disabled` and notify the tenant. Stripe uses exactly this pattern and documents it publicly.
- Sign every webhook payload with HMAC-SHA256 using a per-tenant secret: `X-Webhook-Signature: sha256=<hmac>`. Tenants verify this on their end to confirm the payload came from your platform and was not tampered with in transit.
- Scope webhook subscriptions per tenant in a `webhook_subscriptions` table: `(tenant_id, endpoint_url, events[], secret, active)`. When an event fires, query only the subscriptions for that tenant — never fan out across tenants.

Real-world example: GitHub's webhook delivery system processes over 1 billion webhook deliveries per day and uses the same HMAC-SHA256 signing pattern — their public documentation explicitly recommends verifying signatures before processing any payload.
