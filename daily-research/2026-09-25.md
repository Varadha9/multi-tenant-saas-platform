## Research Note

Tenant isolation combined with shared search infrastructure yields both cost efficiency and consistent low‑latency results.  
- Create separate logical shards or index prefixes per tenant and map them to a common physical cluster; this enables fast pruning of irrelevant data while preserving the economies of scale of a shared engine.  
- Use a search engine like Elasticsearch or OpenSearch with per‑tenant routing keys so that documents are automatically routed to the correct shard, allowing a single query to hit only the tenant’s slice of the index.  
- Implement a tenant‑aware query cache (e.g., cache key = tenantID + query hash) and set TTL based on SLA; caching reduces repeat query latency by up to 70 % for common filters.  
- Enforce row‑level security at the database layer (PostgreSQL RLS) and combine it with API‑level access control so that even if a search request bypasses the index, the underlying data cannot be leaked.  
A mid‑size SaaS project‑management tool serving 12 k SMB tenants migrated from a monolithic MySQL full‑text search to a multi‑tenant Elasticsearch cluster; after the change, average filter query latency dropped from 250 ms to 78 ms and 95 th‑percentile latency improved by 3.2×, while operational cost rose only 12 % due to shared nodes.
