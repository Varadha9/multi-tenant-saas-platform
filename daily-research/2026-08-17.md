## Research Note

GDPR compliance is not optional for any SaaS platform with European users — and the multi-tenant architecture makes it both easier (isolated data) and harder (scale of deletion requests) to comply.

- Map every table that stores personal data (name, email, IP address, device identifiers) and document it in a data processing register. For a multi-tenant SaaS, this means tagging columns at the schema level — add a comment like `-- PII` to relevant columns in your migration files so the register stays in sync with the schema.
- Implement a right-to-erasure endpoint: `DELETE /api/workspace/members/{userId}`. This must hard-delete or anonymize all PII for that user across every table — not just the users table. Use a cascading service that walks all related tables (leads, tickets, attendance records) and replaces PII with `[DELETED]` placeholders while preserving the record structure for audit integrity.
- For data residency, AWS and GCP both offer region-locked deployments. If a tenant's data must stay in the EU, deploy their workspace to `eu-west-1` and store this preference in the tenant configuration. Route their requests to the correct regional deployment via subdomain DNS.
- Store consent records — what a user agreed to, when, and which version of the privacy policy — in an append-only `consent_log` table. Never update or delete consent records.

Real-world example: Notion was fined €290,000 by the French CNIL in 2023 for inadequate data deletion mechanisms — a direct consequence of not implementing proper right-to-erasure workflows.
